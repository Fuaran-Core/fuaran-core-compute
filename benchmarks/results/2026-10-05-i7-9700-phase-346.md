## What was measured

**The steps** are the two morsel cases Layer 6 times (Phase 341): `filter` is `a + b > 500` over two
int columns (no kernel predicate, so the compiled tree runs per morsel), and `derive` is the sheet's
`lines` node, `amount = qty * price` then `big = amount >= threshold`. The columns are Layer 6's
`rowTable` and the corpus's `orders`, with one change: Layer 6 builds `b` as `(i * 104729) % 1000` in
int32, which WRAPS on .NET and does not under Fable, so the two hosts' tables differ from 20,506 rows
on. Here the products are taken exactly on every host (int64 in F#, a double in JavaScript). The
kept-row counts agree across all three programs: 8,870 / 88,700 / 887,000.

**The prototype is the best case for workers.** The worker arm runs hand-written loops over typed
arrays in the shape Phase 326 made the emitted code take (direct indexing, the int add carried in a
double with the overflow test), in 8,192-row morsels (`Kernels.MorselRows`), claimed by `Atomics.add`
from a shared counter by the workers and the caller alike, with the columns already in
`SharedArrayBuffer`s and a warm pool woken by `Atomics.notify`. The SAME loops run on the caller's
thread for the sequential arm, so the arms differ in threading and nothing else. `threads` counts the
caller: 8 threads is 7 workers plus the caller. Every pooled run's answer (the `filter`'s kept rows
in morsel order; the `derive`'s two vectors and their masks) was compared byte for byte with the
sequential arm's, after the outputs were cleared, so a pool that skipped work would have failed. All
72 pooled cells were identical.

**Three hosts.** node (the caller waits with `Atomics.wait`); Edge, the caller on the PAGE's thread
(it must wait with `Atomics.waitAsync`, below); Edge, the caller inside a dedicated worker that owns
the pool (nested workers; it may wait with `Atomics.wait`).

## What the page may do

| page | `crossOriginIsolated` | `SharedArrayBuffer` | `Atomics.wait` on the page's thread |
|---|---|---|---|
| served without COOP/COEP | false | **undefined** | — |
| served with `COOP: same-origin`, `COEP: require-corp` | true | function | **refused**: `TypeError: Atomics.wait cannot be called in this context` |
| a dedicated worker of the isolated page | true | function | allowed |

Without the two headers there is no shared memory at all, so the worker runner has nothing to fall
back FROM except the sequential member. With them, the page's own thread still may not block: a
synchronous member that waits for its pool can only exist off the page's thread.

| Fable on node — the evaluator | filter | 2.44 ms | 25.0 ms | 251 ms |
| Fable on node — the evaluator | derive | 3.75 ms | 38.0 ms | 419 ms |
| node — the prototype's loop, one thread | filter | 0.058 ms | 0.58 ms | 5.98 ms |
| node — the prototype's loop, one thread | derive | 0.073 ms | 0.80 ms | 8.31 ms |

The evaluator's row costs 250 ns (`filter`) and 420 ns (`derive`) under node: **42 to 50 times** the
prototype's loop over the same arrays on the same thread. That gap is the compiled tree's per-row
machinery (closures, the error slot, the null slot, the `ResizeArray` of kept rows, the boxed root),
not the arithmetic, and no number of threads closes it.

The caller alone through the pool's protocol (1 thread: the atomics, no workers) costs what the
sequential arm costs, within 5 per cent under node and in the host worker and 1 to 14 per cent
above it on the page's thread, so the protocol itself is close to free.

**Reading it.** At 10,000 rows (two morsels) a pool buys nothing measurable. From 100,000 rows the
host-worker shape and node scale to 2.8 to 6.3 times on eight threads. The page-thread shape is the
weakest: its waits are promise resumptions on the page's event loop, and at eight threads it is slower
than at four in three of four large cells. Everything here is a loop that costs 5 to 8 ns a row; the
evaluator's rows cost 250 to 420 ns, so on the evaluator the per-row work, not the pool's overhead,
would dominate, and the ratios would be at least these (a projection, not measured: a worker runner over
the evaluator does not exist to measure, for the reasons in the last section).

## Start-up and transfer

| cost | node | Edge, page | Edge, host worker |
|---|---|---|---|
| a cold pool of the prototype's loops, 1 / 3 / 7 workers ready | 28 / 29 / 35 ms | 32 / 14 / 42 ms | 11 / 12 / 21 ms |
| a cold pool importing the Fable-compiled evaluator (`DataFrame.js` and the graph it imports; the compiled output is 2.4 MB on disk), 1 / 3 / 7 workers | 144 / 166 / 284 ms | not measured | not measured |
| copying a million rows of the `filter`'s inputs (two int columns and two masks) into shared memory | 0.83 ms | 2.08 ms | 1.25 ms |
| the same for the `derive`'s (int, float, two masks) | 1.51 ms | 2.99 ms | 1.74 ms |
| copying a million rows of the `derive`'s output (a float vector, a bool vector, two masks) out | 2.25 ms | 3.42 ms | 2.56 ms |
| the sequential step over SHARED buffers against plain ones, a million rows | +7% filter, -1% derive | +4% filter, +4% derive | +5% filter, -1% derive |

The pool's start-up is paid once per page, but a worker that compiles a step from data must load the
evaluator, and that is 144 ms for one worker and 284 ms for seven under node — the cost of roughly
two hundred million-row `filter`s on the pool. Copying a million rows in and out costs 2 to 6 ms,
which is 60 per cent of the pooled prototype `filter` and three times the pooled `derive`: if the frame's vectors do not already live in
shared memory, the copy eats most of what the pool buys on a loop this cheap.

## What the shard assumed, checked against the tree

1. **"The frame's numeric vectors already compile to typed arrays."** Half true. Under Fable `int[]`
   and `float[]` are `Int32Array` / `Float64Array`, but every `bool[]` — every column's validity mask,
   and the `Bools` vector — is a plain JavaScript `Array` (`fill(new Array(n), false)`), and `Strs`,
   `Decs` and `Cells` vectors hold strings and objects (`Frame.fs`, `Vec`). Only the VALUES of int and
   float columns could live in a `SharedArrayBuffer` today; the masks would have to change
   representation under Fable, and a string, decimal or boxed column cannot be shared at all.
2. **"The runner as the JavaScript member of the kernel pair."** Not as the pair stands. The member
   it would replace is `RunMorsels: int -> (int -> bool) -> unit`, whose `body` is a CLOSURE over the
   frame, the compiled tree, the environment and the caller's `kept` / `errors` arrays
   (`DataFrame.fs`, the compiled `Filter` and `evalDerivedColumn`). A closure cannot cross into a Web
   Worker; a worker must receive the step as data, compile it itself against its own view of the
   frame, and write its rows somewhere the caller can read. And the pair is SYNCHRONOUS: the page's
   thread may not `Atomics.wait` (measured above), so a synchronous member can wait for its pool only
   when the whole evaluator runs in a dedicated worker; on the page's thread only an asynchronous
   evaluation entry point could, and that changes the evaluator's public signature on one host.
3. **"Plausible."** The parallel part is: every pooled answer was byte-identical to the sequential
   one, as it must be for row-local steps whose morsels write disjoint rows and are concatenated in
   morsel order.
