# Compute benchmarks — 2026-10-03, Snapdragon X Elite (X1E80100), Phase 341 (Layer 6 re-measured natively, Arm64)

Phase 270 shipped the host kernels (`Kernels.fs`: the comparison and bitmap kernels and the morsel
runner behind `Filter` and `Derive`), and it removed an order-preserving parallel `GroupBy`. Every
timing behind those verdicts was taken with the **x64** .NET build running **under emulation** on
this Arm64 machine: BenchmarkDotNet reported `X64 RyuJIT x86-64-v3`. Emulation penalises the two
things being judged, intrinsics and thread scheduling. This file re-takes those measurements with the
native Arm64 JIT. The x64 half is measured natively on the i7-8650U and recorded in that machine's
own file.

The 270 figures came from an unrecorded harness over `prepare` / `evalPrepared`. The figures here
come from the committed `Layer6` suites, so read the two columns as verdicts side by side, not as one
series.

| Build | Release. BenchmarkDotNet builds each measured process itself with `-c Release` |

**The figure is the median** (BenchmarkDotNet's `Median`). The main run took 16 min 56 s for 66
benchmarks. The morsel sweep rebuilt the harness with `Kernels.MorselRows` set to 4,096, 16,384 and
32,768 and ran the `Morsels` suite at each. Those edits were never committed, and the constant is
8,192 at this commit. Every suite's `GlobalSetup` asserts its answers before anything is timed:

- the member under test agrees with the portable member;
- a row case evaluated at least as many rows as it holds, so no planner rewrite moved the `Limit`
  ahead of the work;
- the rebuilt `GroupBy` equals the sequential step, cell for cell, with the expected group count.

No other benchmark ran alongside this one. Other sessions on the machine were not controlled, so
same-run ratios carry the verdict, not absolute times.

How to reproduce:

```powershell
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks -- --filter '*Layer6*'
```

## The corpus

- **KernelPair:** each kernel alone over `Rows` values. Ints over 0 .. 999 and floats in quarters
  over 0 .. 249.75, with one row in 97 absent. The cases are `CmpInts (>= 500)`, `CmpFloats (< 125.0)`,
  `And` and `Or` of those two bitmaps, and `Selection` of their conjunction.
- **Comparisons:** `Filter`s answered by the bitmap kernels, through `evalPreparedCountedWith`, then
  `Limit 10`. `cmp` is `a >= -10` (every row kept). `cmp-and` is `a >= 100 and x < 200.0`.
- **Morsels:** `compiled` is `a + b > 500`, no kernel predicate, so it runs one compiled tree per
  morsel. `derive` is the sheet's `lines` node (two `Derive`s) over `orders`. Both end in `Limit 10`.
- **ParallelGroupBy:** `GroupBy k [Sum v as total; Count v as n]` over an int key at 10 keys or at
  `Rows / 10` keys, visited in a scrambled order, with a float `v` in whole quarters. `sequential`
  is the shipped step. `morsel-merge` is 270's described prototype: each 8,192-row morsel is grouped
  by the shipped step on the thread pool, and the morsel tables are merged in morsel order on
  first-seen key.

Against 270's emulated figures for the same two arms, the sequential step at 10 keys went from
13.8 ms (100k) and 408 ms (1M) to 0.57 and 6.15 ms. That is Phase 323 and the native JIT together,
and this file does not separate them. At one key per ten rows, each morsel's table holds nearly as
many groups as rows, so the merge re-probes and re-allocates almost the whole input. A partition by
group (Phase 344) never builds those tables.
