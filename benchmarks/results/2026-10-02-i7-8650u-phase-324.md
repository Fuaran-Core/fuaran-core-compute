# Compute benchmarks — 2026-10-02, Intel Core i7-8650U, Phase 324 (window and sort under order codes)

Phase 324 takes the `Window` step off the row form and puts `Sort` on order codes. A window no
longer gathers its partitions into row lists and sorts them with `List.sortWith` under the boxed
row comparator: each row's partition is a slot from the typed key slots a `GroupBy` over the same
columns forms, one permutation lists the rows partition by partition in window order, and each
partition is a run of it scanned in sequence. Sort keys become ORDER CODES (`DataFrame.Ordering`):
an `int` offset from its least or greatest value, `string` / `float` / `decimal` values dense-ranked
once through their existing total order, `bool` 0 / 1, a null past every value; where the ranges
allow, the codes and the row's position pack into one exact number and the sort compares plain
numbers. A key column holding a cell outside its type keeps the comparator (and the window its
per-partition stable sort), so its answer is unchanged. The public `windowStep` and the incremental
seam's window step share the frame path.

## Instrument

.NET 10 (SDK 10.0.203 band), Release, a console probe compiled once against each of three trees —
8a39a42 (the shard's baseline), cac7980 (the pre-phase tree, `v0.37.0`) and the phase's tree —
under the assembly name the dataframe package grants its internals to, so it times
`DataFrame.evalStep` over a prepared frame (the step alone) as well as `DataFrame.evalPipeline`
(Table in and Table out). A warm-up of at least 20 calls and 500 ms; calls per sample doubled until a
sample spans 50 ms; seven samples with a forced GC before each; best and median per call; allocation
is `GC.GetAllocatedBytesForCurrentThread` across a sample divided by its calls. The trees ran back
to back in one script.

The machine was **heavily loaded** (other sessions held it at about 90% CPU throughout, and one
earlier round read every tree two to three times slower than the round below). Allocation does not
move with load; times do, and only same-run comparisons are claimed. The node figures are a probe
over the same shapes compiled by Fable 5.0.0 against each tree's sources and run under node v22.20.0,
timed with the wall clock, best and median of three samples, two rounds interleaved across the trees.

The shapes, all at 100,000 rows: the corpus window table (`seq`, `v` ints; `CumulSum` of `v` by
`seq`); the corpus sort table (`k1` a string over 100 values ascending, `k2` a permuted int
descending); and a wide table of a five-value string partition `p`, a 100-value string `k1`, a
permuted int `k2`, a permuted float `f`, a 100,000-value string `s` and a float `v`.

## The tick family

A window ticks through the seam's restricted walk, which recomputes the window's column over the
whole frame (`RecomputeFrame`), so the tick costs about the diff plus a full window: a faster window
makes the tick cheaper by the same amount and the RATIO rise, which the phase was written expecting.
It measured that before it shipped and cut the walk's window step to match:

1. the step reads the columns the window reads, each packed once (straight from the source list
   where the column is still it), and shares every other column as a `Derive` does, where it had
   built a row array per row, appended the column to each and copied every column back;
2. a window is read in place as a sort is (it moves no row; the walk clears the in-place reading at
   it);
3. with every slot alive in slot order, the appended column is built as the cell list the result
   hands back and carried as the column's origin, where it had been stored cell by cell into a slot
   array first. Measured at 20,000 rows with a stopwatch inside the refresh, that fill cost 1.3 to
   1.4 ms against 1.0 ms for the whole window step of the full evaluation: each boxed cell stored
   into an array that size is a reference from an old-generation object to a young one.

Measured with the probe (tick = `Delta.diff` plus `Incremental.refreshOn` after a one-row edit,
against `evalPipeline` of the edited table):

|---|---:|---:|---:|---:|---:|---:|---:|
| window CumulSum | 1,000 | 0.764 ms | 0.561 ms | x1.36 | 0.100 ms | 0.074 ms | x1.35 |
| window CumulSum | 100,000 | 249.5 ms | 185.2 ms | x1.35 | 21.7 ms | 16.8 ms | x1.30 |
| sort two keys | 1,000 | 0.093 ms | 0.390 ms | x0.24 | 0.099 ms | 0.138 ms | x0.72 |
| sort two keys | 100,000 | 26.6 ms | 130.3 ms | x0.20 | 26.1 ms | 34.1 ms | x0.77 |

The window's tick falls eight to eleven times and its ratio holds where it was; the refresh now
costs what the full evaluation costs, and the tick is the diff more. The cuts were each needed: the
first cut of this phase (the window fast, the seam's step unchanged) read x5.4 to x5.7; with (1)
alone x2.0 to x2.5, and with (1) and (2) the gated clock leg read `window CumulSum` at 20,000 rows
x1.74 to x1.83, red on all three counted attempts. On the final code the Release clock leg read
`window CumulSum` x1.38 / x0.98 / x1.09 at 1,000 / 20,000 / 100,000 rows (bound x1.6 plus the
0.170 ms floor), `sort two keys` x0.63 / x0.77 / x0.81, and `filter > sort > limit` (whose full
evaluation is the top-n, unchanged) x0.44 / x0.61 / x0.65, every case green on its first counted
attempt. The sort's ratio rises (x0.2 to x0.8) because its full evaluation is four times cheaper;
its tick is unchanged.

## The top-n stays on the comparator

The phase asked for the top-n on the coded path too. It was built and measured, and NOT kept: the
heap compares most rows once, against its root, so coding a key spends a pass over every row (and,
for a string, float or decimal key, a sort of its distinct values) to save about one comparison per
row. Over 100,000 rows with a limit of 10 an int key read 12.0 to 12.6 ms coded against 12.0 to
12.3 ms on the comparator in three paired rounds, allocating 1.2 MB more; a string key pays its
ranking outright. Its order is the same total order either way — the codes tie exactly where the
comparator does, which the ordering law holds — so nothing about the answer depended on the choice,
and the reasoning is recorded beside `evalTopN`.
