# Keyed verbs by key type (D61): a date, a timestamp and a decimal key coded by value

x64, 32 logical processors, Windows 11, .NET 10, Release, BenchmarkDotNet v0.15.8, `--memory`, Core 0.41.0. The
machine was not isolated, so the times are approximate. The allocations are stable and are the stronger evidence.

The keyed family (`*Suites.Keyed*`, new with this change) keys a join and a group-by by one set of distinct values
carried five ways: an int, an id-shaped string (`cust-` and six digits), a date (the day), a millisecond timestamp
and a decimal (hundredths). Every key is distinct
and the join matches each row once, so both verbs answer one row per input row. "Before" is the coder at the commit
before D61, run with the same benchmark sources.

## Verdict

| Question | Answer |
|---|---|
| What did a non-int key cost? | 20 to 33 times the int key at 100,000 rows, joins and group-bys alike: one string rendered per row on each side |
| What does it cost now? | A date key what an int key does. A timestamp key 4.0 to 4.2 times, a decimal key 5.1 to 7.1 times |
| Where is the rest? | The timestamp and decimal dictionaries grow from empty; the date key has a direct table, as the int key does |
| And a string key? | Untouched by D61, and 3.7 times the int key: the level the timestamp key is now at, which puts the remaining cost in the dictionary rather than in any one type |

The string rows were taken in a second pair of runs beside the int key (its own before and after), since a string
carrier now reaches its dictionary through `strCodeOf`'s function value: no cost shows. The int rows did not move by code; their differences, up to 12% at 10,000 rows, are this machine's noise between the
two runs. The date key's bytes now equal the int key's to the kilobyte.

## Still open

- **The timestamp and decimal keys code through dictionaries that grow from empty.** At 100,000 distinct keys that is
  most of their remaining 11 to 14 MB over the int key, and D60 left the same point open for the int dictionary.
  Presizing from the row count over-allocates for a low-cardinality group-by; not attempted.
- **A decimal key pays a floating remainder per trailing-zero test** in `decCode`. Not measured on its own.
