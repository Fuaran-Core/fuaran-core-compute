# Phase 730 — the general product's two speeds on .NET, measured (2026-11-25)

The cause behind DECISIONS.md D89 item 9's "a function no pair serves measured slower on the final tree": taken after
Phase 730 shipped, on the same machine as [`2026-11-24-i7-8650u-phase-730.md`](2026-11-24-i7-8650u-phase-730.md)
(an Intel Core i7-8650U laptop, four cores and eight logical processors with Hyper-Threading, Windows 11, .NET SDK
10.0.203, Release, not a quiet machine). Every figure D89 item 9 quotes from this measurement is in one of the four
captures beside this file, verbatim as the runs printed them.

## What was measured

A console program that does nothing but time `Multivector.geometricProduct`, the general 1,024-term fold, on point ×
sphere operands, one fresh process per line: one second of warm-up, then fifteen samples of about 100 ms, and it
prints the median nanoseconds per product (then the fastest, the slowest and a checksum, which the captures cut). It
was built twice, against the Release assemblies of `Fuaran.Compute.GeometricAlgebra` at the final tree (`318b6bb`)
and at the tree before Phase 730 (`f8a358f`, "base").

```fsharp
// Times Multivector.geometricProduct (the general 1,024-term fold) on point * sphere operands, in one
// fresh process: 1 s warm-up, then 15 samples of about 100 ms; prints the median ns per call.
open System
open System.Diagnostics
open Fuaran.Compute.GeometricAlgebra

let orFail r = match r with Ok x -> x | Error e -> failwithf "%A" e

[<EntryPoint>]
let main argv =
    let rng = Random 730
    let c () = rng.NextDouble() * 20.0 - 10.0
    let n = 64
    let ps = Array.init n (fun _ -> Point.up (c (), c (), c ()) |> orFail |> Point.toMultivector)
    let ss = Array.init n (fun _ -> Sphere.ofCentreRadius (c (), c (), c ()) (0.5 + 4.5 * rng.NextDouble()) |> orFail |> Sphere.toMultivector)
    let mutable sink = 0.0
    let pass (count: int) =
        for k in 0 .. count - 1 do
            let i = k &&& (n - 1)
            let r = Multivector.geometricProduct ps[i] ss[i]
            sink <- sink + Multivector.coefficient 1 r
    let sw = Stopwatch.StartNew()
    while sw.ElapsedMilliseconds < 1000L do pass 1000
    let samples =
        Array.init 15 (fun _ ->
            let t = Stopwatch.StartNew()
            let mutable calls = 0
            while t.ElapsedMilliseconds < 100L do
                pass 1000
                calls <- calls + 1000
            t.Elapsed.TotalMilliseconds * 1e6 / float calls)
    Array.sortInPlace samples
    printfn "%.0f %.0f %.0f %g" samples[7] samples[0] samples[14] (sink % 1.0)
    0
```

The GC capture uses the same program with the timing replaced by six measurements of nine 60 ms samples each, a forced
compacting collection between them:

```fsharp
// Times Multivector.geometricProduct (the general 1,024-term fold) on point * sphere operands, in one
// fresh process: 1 s warm-up, then 15 samples of about 100 ms; prints the median ns per call.
open System
open System.Diagnostics
open Fuaran.Compute.GeometricAlgebra

let orFail r = match r with Ok x -> x | Error e -> failwithf "%A" e

[<EntryPoint>]
let main argv =
    let rng = Random 730
    let c () = rng.NextDouble() * 20.0 - 10.0
    let n = 64
    let ps = Array.init n (fun _ -> Point.up (c (), c (), c ()) |> orFail |> Point.toMultivector)
    let ss = Array.init n (fun _ -> Sphere.ofCentreRadius (c (), c (), c ()) (0.5 + 4.5 * rng.NextDouble()) |> orFail |> Sphere.toMultivector)
    let mutable sink = 0.0
    let pass (count: int) =
        for k in 0 .. count - 1 do
            let i = k &&& (n - 1)
            let r = Multivector.geometricProduct ps[i] ss[i]
            sink <- sink + Multivector.coefficient 1 r
    let sw = Stopwatch.StartNew()
    while sw.ElapsedMilliseconds < 1000L do pass 1000
    let measure () =
        let samples =
            Array.init 9 (fun _ ->
                let t = Stopwatch.StartNew()
                let mutable calls = 0
                while t.ElapsedMilliseconds < 60L do
                    pass 1000
                    calls <- calls + 1000
                t.Elapsed.TotalMilliseconds * 1e6 / float calls)
        Array.sortInPlace samples
        samples[4]
    let line =
        [ for _ in 1 .. 6 do
              let m = measure ()
              GC.Collect(2, GCCollectionMode.Forced, true, true)
              GC.WaitForPendingFinalizers()
              yield sprintf "%.0f" m ]
    printfn "%s %g" (String.concat " " line) (sink % 1.0)
    0
```

A busy thread is a PowerShell loop pinned to one logical processor:

```powershell
param([int]$Mask, [int]$Seconds)
$p = [System.Diagnostics.Process]::GetCurrentProcess(); $p.ProcessorAffinity = [IntPtr]$Mask
$end = [DateTime]::UtcNow.AddSeconds($Seconds); $x = 0
while ([DateTime]::UtcNow -lt $end) { for ($i = 0; $i -lt 100000; $i++) { $x++ } }
```

Processes were pinned with `start /b /wait /affinity <mask> dotnet Probe.dll`. Logical processors 2k and 2k + 1 are the
two hyper-threads of physical core k.

## The captures

- [`jit.txt`](2026-11-25-i7-8650u-phase-730-two-speeds/jit.txt): twelve processes with `DOTNET_JitDisasm=general` and
  `DOTNET_JitStdOutFile`. Each line gives the median, a hash of the tier-1 listing of `Kernel.general` with its
  embedded addresses masked (a static base and two type handles), the listing's size and the tiers it went through.
  Every process compiles the same 293 bytes through the same tiers, the slow one included (4729 ns). In earlier runs
  of the same program, not captured to files, a slow listing and a fast one differed in one line only, the address
  of a static base, and `DOTNET_JitDisasmWithAlignmentBoundaries=1` placed the 32-byte boundaries identically in both.
- [`gc-flips.txt`](2026-11-25-i7-8650u-phase-730-two-speeds/gc-flips.txt): twelve processes, six measurements each, a
  forced compacting collection between measurements. Two processes change speed after their code is final:
  2054 → 4688 → 4687 → 4741 → 2132 → 2050, and 2391 → 4204 → 2612. A blocking collection lets the scheduler move the
  thread to another logical processor.
- [`affinity.txt`](2026-11-25-i7-8650u-phase-730-two-speeds/affinity.txt): the probe pinned to logical processors 2
  and 4 (two different physical cores), six processes per row, for each tree:

  | Condition | Final tree, ns | Base tree, ns |
  |---|---|---|
  | Sibling processors 3 and 5 idle (not reserved: other programs may use them) | 1866 to 2327 | 1925 to 2785 |
  | Busy threads on the siblings 3 and 5 | 3872 to 7257 | 4807 to 5138 |
  | Busy threads on processors 0 and 6, other cores | 2400 to 3821 | 2654 to 6024 |

  With both siblings busy every process ran at the slow speed, on both trees. With the busy threads on other cores the
  probe ran at 2400 to 3132 ns but for two runs, one per tree (3821 and 6024). Nothing kept the machine's other
  programs off the siblings, and the fast speed is slower when more cores are busy, as turbo frequency falls.

- [`tiered-pgo-off.txt`](2026-11-25-i7-8650u-phase-730-two-speeds/tiered-pgo-off.txt): thirty unpinned processes of
  the final tree with `DOTNET_TieredPGO=0`, sorted: 2091 to 2593 ns, and one at 4469. Turning dynamic profile-guided
  optimisation off does not remove the slow speed.

## What it shows

The two speeds are the product's thread running alone on its physical core, or sharing it with another busy thread.
They are not a property of the code. The JIT's code is the same in both, and the two trees run at the same two speeds
under the same conditions. Fixed for a process and flipping at a blocking collection is the scheduler keeping a
thread on its ideal processor, and moving it when the thread blocks. The base's seven fast runs and the final tree's
five slow runs in the harness were taken at different times on a machine that was not quiet. That is what separates
them, not Phase 730.

Not measured here: another machine or processor, Linux, node, and the specialised fold's own slow mode (D89 item 8),
whose proportion matches but which was not run under pinning.
