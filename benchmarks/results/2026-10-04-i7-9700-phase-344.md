# Phase 344 — the gathering verbs across threads, native x64

Intel Core i7-9700, 3.00 GHz, 8 physical cores (no SMT), Windows 11, .NET 10.0.12, X64 RyuJIT
(x86-64-v3); the harness refuses an emulated process (Phase 341). BenchmarkDotNet 0.15.8, one
launch, three warm-ups, ten measured iterations; the figure is the **median**.

```
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks -- --filter '*Partitioned*'
```

The corpus (`benchmarks/Fuaran.Core.Compute.Benchmarks/Partitioned.fs`): `k` an int key over ten
values (`ten`) or one value per ten rows (`tenth`), visited in a scrambled order; `s` a permutation of
`0 .. n - 1`; `v` a float in whole quarters. The sort and the top-n order by `k` then `s`; the window
partitions by `k`, orders by `s` and takes `CumulSum v`. At `ten` the sort keys pack with the
position into one number (`SortFinite`); at `tenth` and a million rows they do not, and the positions
are sorted under the total order (`SortPositions`). The top-n is `Sort` then `Limit 10`, fused.

Only one native machine was measured: the Arm64 leg (Snapdragon X1E80100) was not run in this phase.

The machine was not quiet for every sitting: another session's eight node processes held the CPU
for part of the afternoon. The full sitting below ran with it at about half load; the join figures
were taken with it at about 60 per cent and are read for direction only.

## Kept: the sort, the top-n and the window

Native member against portable, median.

| Verb | Keys | 10,000 | 100,000 | 1,000,000 |
|---|---|---|---|---|
| sort | ten | 0.596 / 0.600 ms (below threshold) | 3.61 / 7.13 ms (**1.98x**) | 38.5 / 84.4 ms (**2.2x**) |
| sort | tenth | 0.582 / 0.618 ms | 3.59 / 7.26 ms (**2.0x**) | 81.1 / 383.4 ms (**4.7x**) |
| top-n | ten | 0.193 / 0.172 ms | 0.583 / 1.623 ms (**2.8x**) | 3.79 / 16.52 ms (**4.4x**) |
| top-n | tenth | 0.171 / 0.153 ms | 0.529 / 1.519 ms (**2.9x**) | 3.50 / 14.47 ms (**4.1x**) |
| window | ten | 0.648 / 0.658 ms | 4.24 / 8.25 ms (**1.9x**) | 48.4 / 134.2 ms (**2.8x**) |
| window | tenth | 0.527 / 0.526 ms | 3.76 / 5.92 ms (**1.6x**) | 66.7 / 262.0 ms (**3.9x**) |

At 10,000 rows both members run the same sequential code (`PartitionRows` = 32,768); the top-n's
12 per cent there is the same code in two processes. The native sort allocates about a fifth more
(the merge buffer); the window about a sixth more.

## Not kept: the grouping by key across threads

Built in the evaluator as the shard describes — rows hashed by key into one partition a logical
processor, each partition's groups numbered and folded in row order on its own thread, the groups
merged on their first logical rows — and measured against the shipped grouping. The harness keeps
the prototype (`GroupByKey`), specialised to the corpus' step (`Sum` and `Count` of `v` by `k`).

| Keys | 10,000 | 100,000 | 1,000,000 | Allocated at 1,000,000 |
|---|---|---|---|---|
| ten | 0.191 / 0.103 ms (1.85x slower) | 1.632 / 1.120 ms (1.46x slower) | 6.92 / 11.01 ms (**1.59x faster**) | 21.5 MB / 7.8 MB |
| tenth | 0.213 / 0.123 ms (1.73x slower) | 2.571 / 1.231 ms (2.09x slower) | 12.57 / 14.63 ms (1.16x faster) | 30.9 MB / 13.3 MB |

The evaluator's generic form (any hashable key, any streamed aggregate) read 9.3 against 10.9 ms
and 13.0 against 15.2 ms at a million rows, in a sitting under load. With the threads held to one
(the partitioned path run sequentially), the partitioned form costs about 22 ns a row against the
sequential grouping's 10: each partition reads its rows scattered across the whole vector, and the
hashing and placing passes are work the sequential path never does. Eight threads recover that and
little more.

## Not kept: the join probe over ranges of left rows

The left rows coded and looked up a range at a time on the pool (a read-only probe of the built
index), against the sequential probe; one sitting, under load.

| Keys | 100,000 | 1,000,000 |
|---|---|---|
| ten | 5.19 / 4.19 ms (1.24x slower) | 47.4 / 56.7 ms |
| tenth | 4.96 / 5.31 ms | 69.7 / 53.0 ms (1.31x slower) |

No consistent gain: the probe is a small part of a join, whose cost is the emission of the matched
pairs and the gathers of every output column.

## The grouping's key column (both members)

Measured before any threading: at one key per ten rows the grouping spent most of its time boxing
the KEY cells (a `Cell[]` per group, packed back into a vector), not on the aggregates Phase 323
streamed. Split by stage at a million rows: slot assignment 5.9 ms, the two streamed aggregates
4.6 ms, the whole step 31.7 ms. The key column is now read from each group's first row straight
into the output vector (`DataFrame.keyColumn`): the step reads 14.6 ms at a million rows and 1.23 ms
at 100,000 (from 2.21), on both members. At ten keys nothing moves (11.0 ms).
