# The join's overhead (D60), and a correction to the figure that prompted it

x64, 32 logical processors, Windows 11, .NET 10, Release, `instrument: X64 process on a X64 machine`,
BenchmarkDotNet v0.15.8. The machine was not isolated, so the times are approximate. The allocations are
stable and are the stronger evidence.

## Verdict

| Question | Answer |
|---|---|
| Was the join 9 times a hand-written hash join, as `2026-11-07-x64-date-comparison.md` first said? | No. That harness rebuilt the right table inside the timed run. Measured properly it was about 2.4 times at 100,000 rows |
| Where was the removable cost? | A second table over the codes of a single key, growing output lists, and null handling on a side with no padded row |
| What did removing it buy? | A third off the time and the bytes at 100,000 rows, with no answer changed |

## The harness traps behind the wrong figure

- **The input was built inside the timed closure.** `Corpus.typedPipeline "join"` embeds the right table, so
  calling it per run timed the table's construction too. Doing so again reproduces 9.8 ms and 22.7 MB, the
  figure first reported, against 3.0 ms and 10.7 MB for the join alone.
- **A count of warm-up runs is not a warm-up.** 300 runs at 1,000 rows last about 20 ms, shorter than the
  runtime's tiering delay, so they time unoptimised code: 98 µs where the warmed figure is 29 µs. It also made
  the new code look slower at 1,000 rows in a mixed-size process, which separate processes and a timed warm-up
  did not bear out.

## Still open

- **10,000 rows is the join's worst ratio.** The sample's key values span 100,000, past the direct table's
  limit of four times the rows, so this size codes through a `Dictionary` that grows from empty. Presizing it
  is not a free change: `codesOf` is shared with the group-by, where the rows say little about the cardinality.

## The dated pipeline's tail, traced

`byMonth` at 100,000 rows has a median near 1 ms and a mean near 6.6 ms, so the 4.8 ms and the 9.2 ratio in
`2026-11-07-x64-date-comparison.md` are a mean over a tail. A scratch harness recorded each run's collections and
pause: a 3-second warm-up, then 1,000 runs. The hand arm in the same harness: median 514 µs, mean 543 µs.

| Configuration | Median | Mean | p99 | Runs with a gen2 |
|---|---:|---:|---:|---:|
| Workstation, concurrent (the console default) | 1,016 µs | 6,604 µs | 17.4 ms | 400 |
| Timer resolution raised to 1 ms (`timeBeginPeriod`) | 895 µs | 1,885 µs | 4.4 ms | 400 |
| Workstation, non-concurrent | 1,086 µs | 919 µs | 1.6 ms | 500 |
| Workstation, `GCLOHThreshold` at 32 MB | 526 µs | 570 µs | 0.8 ms | 0 |
| Server, concurrent | 633 µs | 1,029 µs | 16.2 ms | 18 |
| Server, non-concurrent | 638 µs | 1,032 µs | 12.4 ms | 31 |
| Workstation, 200 MB of live small arrays | 588 µs | 720 µs | 7.0 ms | 11 |
| Workstation, 2,000 MB of live small arrays | 543 µs | 611 µs | 0.9 ms | 1 |

What this shows:

- **The slow runs are gen2 runs, and the time is not a pause.** Of 399 runs over five times the median, 398 held a
  gen2, and they averaged 15.3 ms with 0.6 ms of recorded pause.
- **Large arrays trigger it.** Each run allocates about 1.6 MB of arrays over the 85,000-byte threshold, and a heap
  this small collects gen2 every two or three runs. Raising the threshold removes both the collections and the tail.
  Spacing runs 200 ms apart left 40% of them with a gen2, so the count follows allocation, not load.
- **Background collection is what costs.** With it off, the same gen2 count costs no tail. The wait follows the timer:
  at 1 ms resolution it falls from about 15 ms to about 3.5 ms.
- **A larger heap makes it rare.** Gen2 budgets scale with the live heap, so the mean falls from 6,604 µs to 611 µs at
  2,000 MB, about 1.1 times the hand arm.

The likely reading is that an allocation over the threshold waits for the background collection by sleeping. That
is inferred from these results; the runtime's code path was not traced.

Not explained: under server collection, 25 of 28 runs over five times the median held no gen2. At 1,000,000 rows the
tail remains (median 7.1 ms, mean 10.0 ms, 40% of runs with a gen2, no live heap); no live heap was tried at that size.

Separately, allocation sampling shows about 3 MB of the 5 MB per run is per-row `DatePart` garbage, none of it a cause
of the tail: `Str` for the constant part, re-wrapped by `cellOf` per row, and `CivilDate`, the reference record
`civilOfDays` answers in `Fuaran.Core.Column`.
