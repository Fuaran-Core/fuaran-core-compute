# Phase 375 — the step as data: its laws under node and .NET, and what the hand-off costs

Intel Core i7-9700, 3.00 GHz, 8 physical cores (no SMT), Windows 11; node v25.9.0 x64; .NET 10
(Release); the evaluator compiled by Fable 5.0.0 from this tree. Medians of 11 runs after two
warm-ups (the sequential-member comparison: 41 runs on .NET, 21 under node, after three warm-ups,
three alternating sittings). One machine; no browser was measured, for the reason in the last
section.

What landed is the seam the ruling in `DECISIONS.md` D10 sized first: a row-local step as plain
data (`MorselHandOff`, internal, in `DataFrame.fs`), compiled by whatever runs it through the
evaluator's own compile path and row loops, and finished by the caller. No pool, no worker, no
shared memory and no asynchronous entry point landed; `DECISIONS.md` D13 records what did and why the
rest did not.

The harness is beside this file in [`2026-10-06-i7-9700-phase-375/`](2026-10-06-i7-9700-phase-375/):
`handoff.fsproj` compiles the suite's own law file (`tests/Fuaran.Core.Compute.Tests/MorselHandOffLaw.fs`)
and `Program.fs`. Not a member of the solution. On .NET: `dotnet run -c Release -- 11`. Under node:
`dotnet fable handoff.fsproj -o <scratch>/benchmarks/results/2026-10-06-i7-9700-phase-375 --noCache`
from a directory whose tool manifest provides Fable 5.0.0 (the mirrored output root `run-node.ps1`
uses), then `node Program.js 11` there. It exits 1 if any law fails.

## The laws, on both hosts

Every honest runner answers what the sequential member (`Kernels.oneThread`) answers, byte for byte
as canonical wire, refusals included; both perturbed runners go red. The same lines print on .NET
and under node:

| runner | transform vectors, at 1 / 2 / 3 / 8,192 rows a morsel | corpus, 20,000 rows |
|---|---|---|
| in order (one runner, the whole range) | 12 handed off, 0 disagree, at each size | 14 of 14 handed off, 0 disagree |
| reversed (one morsel at a time, last first, each rebuilt and compiled from the data) | 12, 0 | 14 of 14, 0 |
| cloned (each morsel's record through `structuredClone`, run on the clone, its slots cloned back) | 12, 0 | 14 of 14, 0 |
| shifted (PERTURBED: every morsel after the first starts a row late) | — | 11 of 12 answered steps disagree |
| swapped (PERTURBED: kept rows handed back in swapped morsel pairs) | — | 4 of 12 disagree (the filters) |

Under node the `cloned` runner is the one that matters: a structured clone strips every prototype, so
the worker side of the hand-off ran on a plain object exactly as one posted to a Web Worker arrives,
and its results came back through a second clone. On .NET there is no clone and the record is passed.
The suite (`MorselHandOffTests`) runs the same law on .NET with one more honest runner, one morsel a
task on the thread pool.

The corpus is the benchmark sheet's `lines` and its chain (`Corpus.fs`: two derives, a filter on a
bool column, three more derives including an int one) and Layer 6's compiled filter `a + b > 500`
(`Layer6.fs`), alone and before a second filter and a derive over its selection, plus two steps that
refuse in two morsels (an int overflow at rows 9,000 and 17,000). Every root a hand-off carries is
reached: a filter, and int, float and bool derives. The refusals answer the FIRST morsel's error in
row order under every runner, the reversed one included, because the caller re-runs the first
failed morsel on its own thread.

Of the transform vectors' steps, 12 are handed off. The rest are declined, and run as they always
ran: most of the sample's filters are comparisons of a column with a constant, which Phase 270's
bitmap kernels answer, and many steps read a string or decimal column.

## The sequential member, before and after

The refactor moved the `Filter` and `Derive` row loops into `filterMorsel` and `deriveMorsel` so the
hand-off runs the same ones. A `Filter`'s kept rows now land in one buffer, each morsel from its own
offset, where before each morsel filled a `ResizeArray` and the morsels' arrays were concatenated.
Milliseconds, the median of the three sittings, `Kernels.oneThread`, one step over a frame:

| host | step | rows | before (032e5f8) | after |
|---|---|---|---|---|
| .NET | filter | 100,000 | 5.47 | 5.51 |
| .NET | filter | 1,000,000 | 21.17 | 20.66 |
| .NET | derive | 100,000 | 4.06 | 3.69 |
| .NET | derive | 1,000,000 | 14.46 | 13.19 |
| node | filter | 100,000 | 19.39 | 11.82 |
| node | filter | 1,000,000 | 205.27 | 112.98 |
| node | derive | 100,000 | 8.53 | 8.19 |
| node | derive | 1,000,000 | 117.38 | 104.73 |

Nothing got slower. Under node the filter is 1.6 to 1.8 times faster: the kept rows no longer go
through a growable list. One node sitting of the `after` arm read 154.8 and 165.5 ms at a million
rows; the other two agree with the figures above.

## What a hand-off costs, on one thread

Milliseconds. `plan` is the step and its environment through the wire and back (the exactness check),
the masks and bool values copied to bytes, the slots allocated; `rebuild` is what a runner pays before
its first morsel (the wire decoded, the bytes copied back to the evaluator's arrays); `morsels` is
every morsel run by one runner through the evaluator's own loops; `finish` is the caller's
concatenation or column assembly.

| host | step | rows | sequential | plan | rebuild | morsels | finish |
|---|---|---|---|---|---|---|---|
| node | filter | 10,000 | 1.12 | 0.15 | 0.09 | 1.23 | 0.02 |
| node | derive | 10,000 | 0.75 | 0.18 | 0.08 | 0.83 | 0.03 |
| node | filter | 100,000 | 11.94 | 0.62 | 0.74 | 11.66 | 0.08 |
| node | derive | 100,000 | 7.92 | 0.74 | 0.77 | 8.06 | 0.35 |
| node | filter | 1,000,000 | 114.14 | 4.91 | 8.71 | 119.25 | 0.62 |
| node | derive | 1,000,000 | 110.45 | 8.00 | 9.67 | 86.89 | 4.06 |
| .NET | filter | 10,000 | 0.22 | 0.03 | 0.01 | 0.22 | 0.00 |
| .NET | derive | 10,000 | 0.12 | 0.03 | 0.01 | 0.13 | 0.01 |
| .NET | filter | 100,000 | 2.40 | 0.26 | 0.15 | 2.39 | 0.05 |
| .NET | derive | 100,000 | 1.41 | 0.28 | 0.13 | 1.34 | 0.09 |
| .NET | filter | 1,000,000 | 23.34 | 2.21 | 1.36 | 23.17 | 0.11 |
| .NET | derive | 1,000,000 | 13.87 | 2.57 | 1.18 | 14.21 | 0.70 |

**Reading it.** Run on one thread, the morsels cost what the sequential member costs: the hand-off adds
no per-row work, which is what one compile path and one row loop should give. Its fixed costs are the
copies, and under node they are 4 to 7 per cent of the step at a million rows for `plan` and 8 to 9
per cent for each runner's `rebuild`. The `rebuild` is paid by EVERY worker, because each turns the
byte masks back into the evaluator's `bool[]`: at seven workers and a million rows that is about
60 ms of copying, half the sequential `filter`. It is the cost D10 item 4a named and this phase's
third task removes (the masks as byte arrays in the frame itself), and the reason the pool did not
land ahead of it.

The first node figure for `plan` was 351 ms at a million rows: the byte copies indexed through Fable's
checked `item` / `setItem`. Read and written unchecked (`Raw.get` / `Raw.set`, the loops proving
every index) they cost the figures above.

## Not measured, and why

The pool, the page's thread, a dedicated worker in Edge, and the start-up of workers importing the
evaluator: nothing that runs them exists in the package yet (`DECISIONS.md` D13). Phase 346's figures
stand as the prototype's best case: 2.8 to 6.3 times under node and 3.6 to 4.8 times in Edge from a
dedicated worker, at 100,000 rows and up; 144 ms for one worker and 284 ms for seven to import the
evaluator under node.
