# Compute benchmarks — 2026-10-02, Intel Core i7-8650U, Phase 325 (a typed hash join and one typed row hasher)

Phase 325 puts every keyed verb on one typed row hasher (`DataFrame.RowHash`). A CODER gives each key
column's values dense integer codes, read from the typed vector's carrier (an `int`, a `float`, a
`string`; a boxed column through its cells, coded alike), and an INDEX numbers the rows' code tuples:
one code is its own slot, several pack into one exact integer where their ranges allow (a direct
array lookup when the packed range is small), and only otherwise does a hash table over the tuple
answer. An int key column whose range is small is coded through a direct table rather than a
dictionary. The coder takes the relation as an argument: the TOKEN relation for `GroupBy`'s key probe,
`Window`'s partitions, `Distinct`, `Intersect` / `Except` and `Pivot`'s index groups; `cellEq` for the
join and `Pivot`'s on-value match. The join takes its right side as a frame, builds the right key
slots, probes the left, and gathers every output column through a pair of index vectors.

## Instrument

.NET 10 (SDK 10.0.203 band), Release, a console probe compiled once against each of three trees —
8a39a42 (the shard's baseline), fdea31d (the pre-phase tree, Phase 324 landed) and the phase's tree —
under the assembly name the dataframe package grants its internals to, so it times
`DataFrame.evalStep` over a prepared frame (the step alone) as well as `DataFrame.evalPipeline`
(Table in and Table out). A warm-up of at least 20 calls and 500 ms; calls per sample doubled until a
sample spans 50 ms; seven samples with a forced GC before each; best and median per call; allocation
is `GC.GetAllocatedBytesForCurrentThread` across a sample divided by its calls. The trees ran back to
back in one script; the figures above are from the final run, the phase's tree first.

The machine was **shared and loaded** for most of the session (other work held it busy; one earlier
round read every tree two to three times slower than the final one). Allocation does not move with
load; times do, and only same-run comparisons are claimed. The node figures are a probe over the same
shapes compiled by Fable against each tree's sources and run under node v22.20.0, wall clock, best and
median of five samples, the three trees run back to back.

The shapes: the corpus join (two int key columns, permutations of `0..n-1`, every left row matching
one right row), the same against half as many right rows (left, outer, anti), the same against a
float key column (the mixed `Int` / `Float` arm), a two-key join (a string and an int); `Distinct`
over a string and an int column where every row appears twice; `Intersect` / `Except` against a side
sharing half its rows; the corpus pivot (100 index values by 50 on-values); the corpus orders table's
`byRegion` (a five-valued string key), the same with the region an int code, `GroupBy region` alone,
the corpus high-cardinality group-by (n/2 string keys) and a two-key group-by (region, qty).

### node, against Phase 267

The Phase 267 file's node section read its row-frame tree (its "before") and the dense-frame tree
after it, of which 8a39a42 is the successor: the inner join 57.0 against 76.5 ms (after / before 1.34),
the 10,000-key group-by 61.0 against 80.0 (1.31), the 50-on-value pivot 14.63 against 19.88 (1.36), on a
different machine, and over the harness's shapes (its group-by 20,000 rows of 10,000 keys, its pivot
5,000 rows), where the probe's are the corpus's at 10,000 rows (the group-by 5,000 keys). Scaled to
this machine through 8a39a42 (its figure divided by that ratio), the
row-frame figures here are about 50.7 ms for the join (68.0 / 1.34), 30.2 ms for the group-by (39.5 /
1.31) and 31.6 ms for the pivot (43.0 / 1.36). The phase's tree reads 16.8, 13.5 and 37.0 ms: the join
and the group-by well below the row-frame figures, the pivot at 1.17 of its estimate in this run and at
0.69 in the node harness's own shape table (below). The pivot's remaining cost is its aggregation over
a cell list per (group, on-value) pair, which the row hasher does not reach.

The node harness (`Node/run-node.ps1 -Runs 3`) compiled and ran to exit 0 on the phase's tree (its
corpus agreements and the decimal-vector law asserted before anything was timed). Its own shape table,
timed late in one long process under load and so noisier than the probe above, read the inner join
10,000 x 10,000 at 57.0 ms against 322.0 on 8a39a42 in the same session, the 10,000-key group-by at 39.0
against 241.0, and the 50-on-value pivot at 41.0 against 81.0: against the row-frame estimates through
the 267 ratios (240, 184 and 59.6 ms), 0.24, 0.21 and 0.69.

## Dictionary-coded string keys on node — measured, declined

Phase 271 declined dictionary-encoded string vectors on .NET evidence: the string key's premium on
`byRegion` (the same pipeline with the region an int code: the same cardinality and row-to-group
assignment, exactly the codes an encoding would hold, with none of its cost at prepare) was 1.8% to
10%, against a 25% bar. The review that wrote this phase read string-key hashing as most of the
`byRegion` grouping step under node and asked for the node figure. It is:

| Tree | Rows | String region | Int region | Premium |
|---|---:|---:|---:|---:|
| Phase 325 | 100,000 | 52.01 ms | 44.51 ms | **16.9%** |
| Phase 325 | 10,000 | 5.50 ms | 5.25 ms | **4.8%** |
| fdea31d | 100,000 | 54.01 ms | 52.99 ms | 1.9% |
| 8a39a42 | 100,000 | 186.99 ms | 198.00 ms | -5.6% |

Best of six (the phase's tree) and of three (the earlier trees), each arm in its own node process.
On the phase's tree the arms alternate and the order reverses halfway, so neither arm always ran
first; on the earlier trees they alternate string first. **The premium is
below the 25% bar on node at both sizes, so no encoding is built**: the .NET decline stands, and it
now has its node clause. The premium is higher on the phase's tree than before it because the INT arm
got faster (an int key column now codes through a direct table), not because the string arm got
slower (54.0 to 52.0 ms). On 8a39a42 the two arms are level: the string-hashing share the review
read is not a string-versus-int premium on any tree measured here.

**Falsifier.** A premium near zero could mean the probe cannot see the key at all; it does see it,
reading the int arm 17% faster at 100,000 rows on the phase's tree, where the int arm has the cheaper
coder. The decision changes if a consumer pipeline's evaluation under node is dominated by a string
key of high cardinality; the 271 file's probe and this one are where to re-read it.

All inside `tick <= 1.6 x full + floor`; the whole leg ran 15 of 15 clock cases green. A combining join
and a pivot are not row-preserving, so the seam answers their tick by re-evaluating through the
reference path: the tick is the diff plus a full evaluation plus the seam's own bookkeeping. A faster
join and pivot make the tick cheaper by the same amount and the RATIO rise, as the phase predicted. The
probe's decomposition on the phase's tree reads the join's tick at 100,000 rows as a 3.5 ms diff and a
45.9 ms refresh against a 28.4 ms full evaluation, and at 1,000 rows as 0.025 + 0.244 ms against
0.200 ms: the seam's re-evaluation costs more than the full evaluation does, a fixed overhead the
300 ms join used to hide. It is held inside the bound at every size, and is the seam's to take, not
this phase's (its region ends at the evaluator). A projected `Distinct` (not a corpus node) ticks the
same way: 0.193 against 0.172 ms at 1,000 rows, 26.7 against 18.6 ms at 100,000.
