# Compute benchmarks — 2026-10-04, Intel Core i7-9700, Phase 358 (the incremental state's encode under node)

Phase 357 measured its packed wire form for `IncrementalEval` under node and found it unchanged
from Phase 355's: at 100,000 rows an encode of 9.2 to 15.6 s and a decode of 6.8 to 8.4 s, against
0.11 to 0.15 s and 0.30 to 0.37 s on .NET (`2026-10-03-i7-8650u-phase-357.md`). This phase profiles
where node's time goes on 357's form, takes the costs that are emission costs rather than work, and
reports what remains.

This is a different machine from 355's and 357's files (an i7-9700 with 48 GB, node v25.9.0, where
those used an i7-8650U and node v22.20.0), so every comparison below is against 357's code
**re-measured here**, its merged tree `4057c40`, under the same harness on the same afternoon. 357's
recorded figures are quoted beside them for orientation only.

## What was taken

Each change is the code the shard named; none moves a public surface and none changes a byte the
encoder writes.

- **The digest over a typed buffer, with no closure per byte.** The managed SHA-256 now writes the
  UTF-8 bytes of 16,384-byte chunks into one byte buffer (a `Uint8Array` under Fable) and compresses
  each chunk's whole blocks in one pass through a module-level function; every index inside it is
  proved by its loop and goes through the evaluator's unchecked `Raw.get` / `Raw.set` (Phase 326),
  and the UTF-16 units are read with `charCodeAt` under Fable, where `s[i]` made a one-character
  string first. The bytes hashed are the ones the per-byte form hashed. This is the one change that
  touches code .NET compiles: the copy is the Fable digest and .NET's runs the platform's SHA-256,
  so on .NET the copy runs only in the suite, which holds it to the substrate's.
- **Ints assembled as one piece.** Under Fable, `intsText` is the engine's own join over the typed
  array, and `appendInt` appends `string i`; Fable's `StringBuilder` keeps every append as a piece
  and joins once, so the digit-a-character form, right on .NET, was a piece per digit there. Both
  under `#if FABLE_COMPILER`, the .NET form unchanged.
- **No checked helper where the loop proves the index.** `readInts` writes its result through
  `Raw.set`, the same plain index on .NET.

The probe is seen to fail: with the chunk carry made off by one, the suite's digest comparison goes
red on the new chunk-crossing strings (a 16,385-unit string), and the harness's corpus check would
refuse the same way under node; restored, both are green.

## The million-row case under node

**It completes under node's default heap on this machine**, which is 4,496 MB here (`v8`'s
`heap_size_limit`, set from the machine's 48 GB). What it needs, found by running under
`--max-old-space-size`:

| What | Live before it (MB) | Completes in | Fails in |
|---|---:|---|---|
| one encode of `filter-groupby` at 1,000,000 rows | 833 (the table and the state) | 1,280 MB | 1,024 MB |
| one decode of it | 873 | 2,048 MB (its result is 817 MB) | 1,536 MB |
| the harness's `state` family up to 1,000,000 rows | — | 3,072 MB | 2,048 MB |

These needs are no larger than 357's code's: its one encode also completes in 1,280 MB and its
decode in 2,048 MB, so this phase did not change the peak, only the time. The encoding's own peak is modest
(well under half a gigabyte above the state it encodes); what 355 and 357 met on a smaller machine
was the harness holding a row's table, edited table, state, encodings, decoded states and refreshes
at once, beside a default heap that is smaller where the machine has less memory. So the harness
keeps its 100,000-row ceiling under node by default, says in that row that it needs a 3 GB heap, and
takes the ceiling as a third argument (`node Program.js 3 state 1000000`) on a host that has one;
the table above was taken that way. Under 3,072 MB the encode at 1,000,000 rows reads 7.6 to 9.9 s,
the collector working near the limit.

## What remains, and whose it is

After this phase an encode under node at 100,000 rows spends 45 per cent of its time in the
substrate's JSON render (`Fuaran.Core.Wire`'s `Json.escape`, which every string of the encoding goes
through) and a decode 51 per cent in its parse (`parseString`). Both walk a string a character at a
time into a `StringBuilder`, which is right on .NET and costs a piece per character under Fable, whose
builder joins its pieces at the end: the same emission cost this phase took out of `intsText`, in
the package below this one. A string that holds nothing to escape, which is every run but the
string runs, could go through whole. That is a change to `Fuaran.Core.Wire`, not to this package,
and it would move the JSON layer of every Fable-hosted consumer of the substrate, not only this
codec; it is reported for the substrate's roadmap rather than worked around here, because working
around it here would mean a second canonical renderer beside the substrate's, which the cross-host
byte-identity this codec rests on cannot afford.

What would remain after that is building the state: the source's cells and lists, and the runs read
back into arrays, which a decode has to build whatever the wire holds, as on .NET.

## Instrument

node v25.9.0, the sources compiled by Fable 5.0.0 (the tool manifest of a sibling that compiles
these packages); .NET 10 (SDK 10.0.401), Release, workstation collector. Intel Core
i7-9700, 8 cores, 48 GB. The machine was in ordinary use (other sessions' builds ran on it at times),
which is why every comparison here pairs two programs run back to back rather than quoting either
alone.

```
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks/Node -- 3 state
pwsh benchmarks/Fuaran.Core.Compute.Benchmarks/Node/run-node.ps1 -FableFrom <dir> -KeepOutput -Runs 3 -Only state
node <kept output>/.../Node/Program.js 3 state 1000000
```

The profiles are `node --cpu-prof` over a small script that imports the compiled modules, primes one
state, encodes it once, then encodes or decodes it ten times; the inclusive figures are each named
function's samples under the codec's entry point, divided by the calls. 357's code is its merged tree
`4057c40`, compiled and run the same way from a separate checkout.
