# Phase 371 — the parallel top-n, and the tick bound against a one-thread evaluation, native x64

Intel Core i7-9700, 3.00 GHz, 8 physical cores (no SMT), Windows 11, .NET 10.0.12, X64 RyuJIT
(x86-64-v3). Operator ruling 2026-10-04 on Phase 344's held item (`DECISIONS.md` D8 item 3), option
A: the tick clock cases compare the incremental tick with the full evaluation AT ONE THREAD, the
bound stays 1.6 and the per-call floor is unchanged, and the top-n a range of rows at a time ships.

## The tick clock cases, before and after

Release, the clock leg alone over the two tick cases:

```
dotnet run --project tests/Fuaran.Core.Compute.Tests -c Release --no-build -- --clock-leg --filter-test-case "table-fed tick"
```

Both columns run the evaluator with the ranged top-n in place. **Before**: the full evaluation
through the host kernels (the native member on every core), as the cases timed it until this phase.
**After**: the full evaluation on `oneThread` (`ScalingTests`) — the native member's vector kernels,
morsels run in order on the caller's thread, never partitioned. The tick arm is the same in both.
Quiet = nothing else of note running; loaded = four `yes > /dev/null` burners on the 8 cores. Every
window counted on its first attempt; none was discarded as saturated. Calibration baseline 3.66 to
3.77 ms quiet, 4.21 ms loaded.

The corpus case's `filter > sort > limit` node (Phase 283), tick against full, ms and ratio:

| Sitting | Rows | Before | After |
|---|---|---|---|
| quiet 1 | 100,000 | 10.82 / 7.02 (**1.54**) | 9.76 / 15.41 (0.63) |
| quiet 2 | 100,000 | 10.89 / 7.25 (**1.50**) | 9.74 / 14.50 (0.67) |
| quiet 3 | 100,000 | 11.27 / 8.51 (1.33) | 9.56 / 14.26 (0.67) |
| loaded | 100,000 | 11.70 / 8.96 (1.31) | 10.87 / 16.51 (0.66) |
| quiet 1 | 20,000 | 1.85 / 3.12 (0.59) | 1.46 / 2.89 (0.50) |
| quiet 1 | 1,000 | 0.071 / 0.139 (0.51) | 0.064 / 0.139 (0.46) |

The `Scaling` case's `tick: filter > sort > limit` (Phase 274) at 100,000 rows: before 1.14, 0.96,
1.07 quiet and 1.03 loaded; after 0.72, 0.73, 0.77 quiet and 0.73 loaded.

The worst cell of either case, every node and size:

| Sitting | Before | After |
|---|---|---|
| quiet 1 | 1.54 `filter > sort > limit` @ 100,000 | 1.31 `inner join` @ 1,000 |
| quiet 2 | 1.50 `filter > sort > limit` @ 100,000 | 1.33 `lines` @ 1,000 |
| quiet 3 | 1.36 `inner join` @ 100,000 | 1.28 `inner join` @ 1,000 |
| loaded | 1.40 `inner join` @ 1,000 | 1.36 `inner join` @ 1,000 |

This sitting read the old comparison green (1.31 to 1.54); Phase 344's three attempts, taken inside
its verify gate, read 1.74, 1.75 and 2.04. Either way the parallel evaluation put the top-n node
alone at the bound's edge, and the one-thread evaluation puts it at about two thirds of the tick's
cost. The other nodes moved the same way or not at all: at 100,000 rows `sort two keys` went from
0.90-1.19 to 0.87-0.96, `window CumulSum` from 0.92-0.99 to 0.73-0.82 and `byRegion` from
0.84-1.00 to 0.75-0.89 (their full evaluations lost the parallel sort and filter morsels too); at
1,000 and 20,000 rows, below the partition threshold, the cells stayed within the sittings' own spread
(the one 1.33 after, `lines` at 1,000 rows, read 0.45 to 0.98 in the other three sittings).

## The top-n, re-measured

```
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks -- --filter '*Partitioned.TopN*'
```

BenchmarkDotNet 0.15.8, one launch, three warm-ups, ten measured iterations; the figure is the
**median**, native member against portable. The corpus is Phase 344's (`Partitioned.fs`): `Sort` by
`k` then `s`, then `Limit 10`, fused by the planner; every setup holds the native answer equal to the
portable one before anything is timed.

| Keys | 10,000 | 100,000 | 1,000,000 |
|---|---|---|---|
| ten | 0.193 / 0.176 ms (below threshold) | 0.561 / 1.659 ms (**2.96x**) | 3.75 / 16.25 ms (**4.33x**) |
| tenth | 0.172 / 0.160 ms (below threshold) | 0.528 / 1.410 ms (**2.67x**) | 3.81 / 14.38 ms (**3.78x**) |

Phase 344 read 2.8x and 2.9x at 100,000 rows and 4.4x and 4.1x at a million: the same within a
sitting's spread. Allocation is unchanged from the sequential heap to within 1.3 per cent (402 KB
against 397 KB at 100,000 rows, 3.92 MB against 3.91 MB at a million).
