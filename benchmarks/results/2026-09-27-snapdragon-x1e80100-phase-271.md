# Compute benchmarks — 2026-09-27, Snapdragon X Elite (X1E80100), Phase 271 (the evidence gate)

Phase 271 proposed dictionary-encoded string vectors and integer (civil-day / epoch-second) date
vectors in the dense frame, **gated on a benchmark showing string grouping, equality or sort, or
date arithmetic, above a quarter of the evaluation of a consumer's own pipeline**. This file is that
measurement, taken on the tree at `593f473` (Phases 262 to 270 landed: the dense frame, chunked
columns, the planner, the host kernels). **The gate is not met, so no encoding was built** — this
file is the phase's whole deliverable.

## Verdict

| Question | Answer |
|---|---|
| Consumer pipelines in the corpus | recipe 02's sheet: `lines` (two `Derive`s, no key) and `byRegion` (`Derive` then `GroupBy region`, a five-valued string key) |
| String grouping share of `byRegion` | **1.8% to 10%** of the evaluation, the ceiling of what any key encoding could remove |
| Date arithmetic share of any corpus pipeline | **0%** — no corpus table, and no recipe 02 node, has a date or timestamp column |
| Threshold | 25% |
| Outcome | **declined by evidence**; nothing in `src/` changes |

The other string-keyed rows in the corpus — the Scaling family's `grp` (17 values), the
10,000-distinct-key group-by, the pivot and the two-key sort — are the suite's synthetic shapes,
not a consumer's pipelines, so the gate does not read them.

The only consumer date use found is fuaran-dotnet's `Binding.Now` composed with `DateDiffDays`
(its `BindingSources.fs` documents the ISO-instant form for exactly that): a scalar evaluated per
render against one instant, not a column the frame groups, compares or sorts at scale.

## How the string share was measured

The question is "how much of `byRegion` would go away if the region key were an integer code?", so
the probe times `byRegion` on the corpus's `orders` table twice: once as the corpus builds it
(`region: StringType`) and once with `region` replaced by an `IntType` column carrying the region's
index in `Corpus.regions` — the same cardinality and the same row-to-group assignment, i.e. exactly
the codes a dictionary encoding would hold, with none of the encoding's own cost at `prepare`. The
difference is therefore an **upper bound** on what the encoding could save for this pipeline.

Each arm is measured through both entry points a consumer uses: `evalPipelineInEnv` over the
`Table` (the boundary paid per call) and `evalPrepared` over a source prepared once. The `GroupBy`
alone (over a two-column `region, amount` table) and `prepare` alone are measured the same way, so
the key's cost in each place is visible.

Instrument: an F# script over the Release build of the benchmark project, referencing `Corpus`
directly. Three warm-up calls, calls per sample doubled until a sample spans 50 ms, a forced GC
before each sample. The final run is **paired and interleaved**: the string and integer arms
alternate AB, BA, … over six rounds, so machine load falls on both alike, and each arm's figure is
its best of six. Every evaluation's `Result` is unwrapped (an error would abort the run), and the
corpus's own `--check` was green on this tree before anything was timed.

### Paired run (the figures this file stands on)

Milliseconds per evaluation, best of six (median beside it).

| Rows | Case | String key | Integer key | Premium of the string key |
|---:|---|---:|---:|---:|
| 10,000 | `byRegion`, `Table` in | 6.502 (6.705) | 6.109 (6.350) | 6.0% |
| 10,000 | `byRegion`, `evalPrepared` | 3.951 (5.209) | 3.747 (4.236) | 5.2% |
| 10,000 | `GroupBy` alone | 1.565 | 1.436 | 2.0% of `byRegion` |
| 10,000 | `prepare` alone | 0.593 | 0.573 | 3.3% of `prepare` |
| 100,000 | `byRegion`, `Table` in | 21.898 (25.221) | 21.494 (26.662) | 1.8% |
| 100,000 | `byRegion`, `evalPrepared` | 14.046 (15.124) | 12.885 (13.958) | 8.3% |
| 100,000 | `GroupBy` alone | 19.126 | 17.242 | 8.6% of `byRegion` |
| 100,000 | `prepare` alone | 9.114 | 8.644 | 5.2% of `prepare` |

For scale, in the same run: the `amount` `Derive` alone costs 0.97 ms at 10,000 rows and 11.4 ms
at 100,000, and the hand arm's whole `byRegion` 0.131 ms and 1.31 ms. The gap between the
evaluator and the hand arm is the frame's boundary, boxing and per-verb overhead, which the key's
representation does not touch.

### The runs that preceded it

An unpaired first run (each arm timed in turn, best of five) read 5.9% at 100,000 rows on the
`Table` path and 6.0% prepared, and 46.7% at 10,000 rows on the `Table` path. That last figure was
the one reading over the threshold, so the probe was re-run in the reverse order: under load, the
reversed run read premiums from -98% to +35%, changing sign between cases, which is noise
swamping the effect in both directions. The paired, interleaved design above was written to answer
exactly that, and it read 6.0% for the case the first run put at 46.7%. The 46.7% was an order
artefact — the first case timed in a fresh `fsi`, sized to four calls per sample — not a property of
the key.

**Falsifier.** Had the string key been costless, the paired `GroupBy`-alone arm would read a premium
near zero or of either sign; it reads the string key 8% to 12% slower than the integer key at both sizes in both quiet runs, so the probe
does see the key's cost — the cost is simply far below a quarter of the pipeline. The finding
changes if a consumer pipeline appears whose evaluation is dominated by a high-cardinality string
key or by a date column at scale; the corpus is the place to add it, and this probe the place to
re-read it.
