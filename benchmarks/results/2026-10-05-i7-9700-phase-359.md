# Compute benchmarks — 2026-10-05, Intel Core i7-9700, Phase 359 (an append-only tick costs the appended rows)

Phase 333 measured an append tick dominated by two passes over every row: `Delta.diff` keyed both
tables to find the old rows where they had been, and the seam re-keyed the new table and re-walked
every step's bookkeeping, so a one-`Project` pipeline's one-row append cost 8 to 18 of its own
evaluations. This phase gives the diff an append path (each column's prefix read once by reference,
the tail alone keyed, its keys checked through a chain an append extends) and the seam an append
reading (Phase 323's in-place reading grown by a tail). Both trees below were measured on this
machine on the same afternoon: the pre-phase tree is `9d0dd1c`, exported whole and built Release.

## Instrument

.NET 10 (SDK 10.0.203 band), Release, an i7-9700 (8 cores) with other workers' builds intermittently
on the machine.

- **The clock leg** (`dotnet run --project tests/Fuaran.Core.Compute.Tests -c Release -- --clock-leg`),
  the gate's instrument, on the phase's tree: its new case "an append tick on every corpus node",
  batched best of five, the full evaluation at one thread (Phase 371), the ratio within one run and
  Phase 285's calibration bracketing every cell.
- **A probe** (an F# script over the Release assemblies, `--optimize+`), run once against the
  pre-phase tree's `Fuaran.Compute.DataFrame.dll` and once against the phase's, alternately: the same
  corpus nodes, the same append (`ColumnOps.AppendRows`' shape, the identity column given keys the
  table does not hold), timing the full evaluation (`evalPipelineInEnv`, the parallel default), the
  diff alone and the tick (diff plus refresh, a fresh table object per call), each the batched best of
  five. Its full evaluation is the parallel one, so its ratios are not the clock leg's; the two trees
  are compared on the same instrument.

The diff is the floor the premise row of the verdict names: 2.5 to 2.7 ms whatever the pipeline, about
one read of the four columns, where the pre-phase diff keyed every row (8.3 to 8.5 ms). A `Filter`'s
tick is the highest because its result is rebuilt: a filter's output columns cannot be the source's
lists, so the refresh unpacks and re-lists them as the evaluation does. A `Project` hands the source's
lists back, so its refresh is 0.38 ms. The window's refresh still packs its columns and lists its
result over the whole frame (Phase 333's "O(n) cheap passes"); its scan is the appended row's.

## node

The append law compiled by Fable and run under node (v25), over the same shapes: a scratch harness
over the phase's sources (a one-`Project`, a `Derive`, a `Filter`, a `Derive > GroupBy` with a count,
an int sum and a float sum, a partitioned `CumulSum`, a `Sort > Limit`), 40 and 300 rows, appends of
1, 7 and n rows, three ticks chained with an edit beside the second. 108 ticks, every delta equal to
the keyed diff's and every refresh to the full evaluation; 36 of 36 perturbed deltas (the edit ticks)
wrong under `Delta.diffTrustingPrefix`. The same harness on .NET printed the same line. The package's
node harness (`Node/run-node.ps1 -Only chain`) compiled and ran green on the phase's tree too.
