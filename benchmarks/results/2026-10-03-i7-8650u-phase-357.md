# Compute benchmarks — 2026-10-03, Intel Core i7-8650U, Phase 357 (a compact form for the incremental state's wire)

Phase 355 gave `IncrementalEval` a wire form and measured it
(`2026-10-03-i7-8650u-phase-355.md`): at 1,000,000 rows on .NET a decode took 11.8 to 12.6 s carrying
its source (6.4 to 7.3 s detached) against 0.09 to 0.38 s for a full evaluation. Phase 357 replaces
that form's one JSON value per cell with typed runs and measures the result on the same machine, the
same pipelines and the same harness.

The two sections after the verdict were written and committed before the form was built: the
profile it was chosen from, and the target. The rest reports against them.

## Where 355's time went, before the form was chosen

Taken on 355's tree, Release build, at 1,000,000 rows of `filter-groupby` and `filter-sort-limit`,
each piece timed on its own (best of two) and the remainder attributed to the walk. Run under `dotnet
fsi` against the Release assemblies rather than in the harness, so the totals read higher and noisier
than the harness's (a collection over a multi-gigabyte heap lands in whichever piece is running); the
proportions are what was used.

| Piece | `filter-groupby` (ms) | `filter-sort-limit` (ms) |
|---|---:|---:|
| Decode, whole | 11,751 | 7,386 |
| the digest over the body (52 and 57 million characters) | 1,669 | 2,507 |
| the parse into `JVal` | 3,883 | 4,065 |
| the walk from `JVal` into cells, tokens and indexes, and the checks | 6,199 | 814 |
| Decode over a supplied source, whole | 8,923 | 5,522 |
| the source's fingerprint (render through `JVal`, then the digest) | 2,707 | 1,938 |
| Encode, whole | 20,707 | 13,597 |
| the source and the members built as `JVal` | 1,998 | 452 |
| their canonical render | 6,179 | 5,918 |
| the digests (the source's, then the body's) | 2,438 | 3,512 |

Three costs, then, in the order they matter:

- **One `JVal` per cell.** The parse allocates a value and a list cell for each of some 8 to 10
  million values, and the walk visits each again to make the cell; the encode builds the same values
  and walks them to render. This is the cost the phase was filed for.
- **The digest.** The package's SHA-256 copy runs at about 30 ns a character on .NET (a closure call
  per byte), which is 15 to 35 per cent of a decode and the whole of a fingerprint's tail.
- **The source's fingerprint** renders the source through `JVal` again where the encoding already
  holds it as text.

## The target, stated before the work

The decode at 1,000,000 rows on .NET is expected to come down **at least threefold**: from 11.8 to
12.6 s carrying the source to **4 s or less**, and from 6.4 to 7.3 s detached to **2.5 s or less**.
The expectation behind the target is nearer 2 to 3 s carrying: the runs remove the per-cell values
from the parse and the walk, and the digest on .NET goes to the platform's SHA-256 (the managed copy
stays the Fable path, value-identical). What cannot move in this phase is the substrate's JSON parser
itself, which still reads every character of a run's string once into a `StringBuilder`, and the
cells and lists the state is made of, which a decode has to build whatever the wire holds. If the
reduction falls short of threefold, it is one of those two, and this file says which.

## The form

Every large member of the state is a **run**: one JSON string holding many values, so the parser
allocates one value per run where it allocated one per cell, and the walk reads the string with a
cursor. The text stays canonical and is the same on both hosts.

- **A column or a cache of cells** names the one case its cells hold (`ints`, `floats`, `bools`,
  `strings`, `dates`, `timestamps`, `decimals`, or `nulls`) and packs the values: ints in decimal and
  floats in the canonical layout, comma-separated, with `NaN`, `Infinity`, `-Infinity` and `-0` as
  tokens; bools one character each; text as `<length>:<text>`. Where a slot is not a value, a mask
  gives one character a slot: a value, the absent cell, or a slot that holds no cell (a row that never
  reached a step). A run of more than one case, an int in a float column for one, is written a value
  a cell, as 355 wrote every run.
- **Row tokens and group tokens** write the prefix they share once (`k:s:r` for this corpus), then
  each remainder length-prefixed.
- **Indexes** (the row-to-group index, the sort orders, a window's orderings, the group members as
  indexes into the row tokens) are packed ints.
- **Row-shaped caches** (the group rows, the aggregate cells, a relation's key cells, a window's
  partition keys) are a matrix: each row's length, then one run per position down the rows, since a
  position holds one case where a row holds several.

The document's version is 2; the reader refuses version 1, which was never released. On .NET the
digest is the platform's SHA-256 over the platform's UTF-8 encoder, fed a chunk at a time; under
Fable it is the package's managed copy, and the suite holds both to the substrate's digest.

The source's fingerprint is taken over its packed encoding, so `sourceFingerprint` no longer
renders the source through a value per cell: in the paired run a decode over a supplied source
spends 2.1 to 2.2 s where 355 spent 6.6 to 8.3.

## Where the time goes now

The same pieces as the profile above, on this phase's tree, at 1,000,000 rows of `filter-groupby`,
under `dotnet fsi` against the Release assemblies (best of two per piece):

| Piece | ms |
|---|---:|
| Decode, whole | 2,729 |
| the digest over the body (40 million characters) | 215 |
| the parse | 436 |
| the source table: four runs into cells, then each column's cell list | 1,049 |
| the row tokens | 169 |
| the group members | 129 |
| the step caches and the row-to-group index | 72 |
| the rest: the plan, the pipeline hash, the alignment checks | about 660 |

The parse and the digest, 47 to 89 per cent of 355's decode in its profile, are 24 per cent of this
one. What remains is building the state: the source alone is four million cells and four lists of a
million, which a decode carrying its source has to build whatever the wire holds, and which is why a
detached decode costs half as much. That is the floor this phase leaves: the column layer holds a
table's cells as a list of boxed cells, and the substrate's parser still reads a run's string one
character at a time into a `StringBuilder`. Neither is this package's to change.

## Instrument

.NET 10 (SDK 10.0.401), Release, workstation collector; node v22.20.0, the sources compiled by
Fable 5.0.0. One program on both hosts, the node harness's `state` family, which this phase extends
with the three per-row columns:

```
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks/Node -- 3 state
pwsh benchmarks/Fuaran.Core.Compute.Benchmarks/Node/run-node.ps1 -FableFrom <dir> -Runs 3 -Only state
```

Each figure is the best of three single calls, wall clock. Before any row is timed the program runs
`IncrementalDelta.stateLaws` over three seeds on its own host, and for each row it asserts that the
refresh from the decoded state, and from the state decoded over its source, equals the refresh from
the original in table and in footprint. 355's binaries were the Release build of its merged tree
(`ffa0e13`), run with the same arguments.

The machine was NOT idle. Other work ran on it throughout (builds and test suites in other
repositories, and a container runtime holding one core), which is why the spread table exists and
why 355's own binaries read 18 to 34 per cent slower here than in 355's file. Read the figures to
their first digit, and the paired ratios before the absolute times.

The profiles are `dotnet fsi --optimize+` scripts against the Release assemblies, timing each piece
on its own through reflection over the internal functions, with a collection before each sample.
