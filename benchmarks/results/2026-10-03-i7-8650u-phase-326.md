# Compute benchmarks — 2026-10-03, Intel Core i7-8650U, Phase 326 (the node emission costs)

Phase 326 takes three costs the JavaScript host paid and the .NET host never did. Fable compiles every
`a[i]` on an `Int32Array`, a `Float64Array` or a plain array to one shared bounds-checked helper
(`Array.item` / `setItem`), which goes megamorphic across the three; every `int64` is a `BigInt`; and
the runtime's `Dictionary` hashes into a map of buckets and reaches a custom comparer through an
interface on every probe. The phase adds:

- **`Raw`** (`Frame.fs`): `get` / `set` emit `a[i]` with no check (`[<Emit("$1[$0]")>]`, under
  `FABLE_COMPILER` only), used only where the loop around the access proves the index — a loop over
  `0 .. n - 1` reading arrays allocated `n` long, or checked once (`within`) to be at least that long,
  or a range test just before the read. Every other index goes through `at` / `put`: the bounds test
  inlined at the call site, refusing with the .NET runtime's own message. On .NET each accessor is
  the plain index, inlined. Through them run the packers, the gathers, `cellAt`, `toTable` / `rowsOf`,
  the portable kernels, the compiled column reads, the Filter and Derive runners, the GroupBy
  stream's `FeedAll`, the row hasher (Phase 325), the order codes and the window (Phase 324), the
  pivot's fill loop and the sort comparator.
- **Float-carried int32 arithmetic**: `arith`'s integer arm (the reference) and the kernel's `intOp`
  carry the result in float64 under Fable and recompute it in int64 only when it leaves the int32
  band — exact inside the band (a sum or difference of two int32s is below 2^33, a remainder below
  its divisor, a product inside the band below 2^53, and a product past 2^53 rounds to a float still
  past the band), so the overflow refusal and its message are the .NET host's.
- **`OpenSlots`**: an open-addressing slot table — linear probing over the key's hash in
  power-of-two arrays kept at most half full, the slot number the caller's, so the order slots are
  numbered in is the order the caller met its keys (first-seen for groups). Under Fable it stands
  where `Dictionary` stands for `CellKey.slots` (its last caller is the seam's maintained grouping),
  the row hasher's per-carrier codes and its packed and wide code-tuple index, and the order codes'
  float and string ranks. On .NET `Dictionary` stays; the table is compiled on both hosts so the
  suite holds it to `Dictionary`.

Two findings from the profiles were emission costs of the same class and are taken too: a
descending `for` compiles to a range enumerator under Fable (`toTable`), and a union's `=` is a
structural comparison call there — `keyComparer` compared `dir = Asc` on every comparison, which made
it the largest cost of the top-n and of every comparator sort. Both are bound once now; the order's
packed keys (finite and non-negative) sort with the engine's own numeric sort.

## Instrument

node v22.20.0, the sources compiled by Fable 5.0.0. Two instruments:

- **The node harness** (`Node/run-node.ps1 -Runs 5`), run on 8a39a42, on 27710d5 and on the phase's
  tree, each tree exported whole; its corpus agreements (the decimal-vector law included, on the trees
  that have it) asserted before anything was timed, exit 0 on all three.
- **A probe** over the same shapes through `DataFrame.evalPipelineInEnv` (Table in, Table out), wall
  clock, two warm-up calls, calls per sample doubled until a sample spans 50 ms, best and median of
  seven samples, the trees alternating in one session and each run twice. Its answer digest is a
  polynomial hash of the answer's canonical wire encoding carried in a double below 2^53, so it reads
  the same digits on both hosts. Compiled for .NET (Release) it is also the .NET differential.

The machine was shared and its load moved through the session: absolute times differ between runs by
up to 2x, so only same-run comparisons are claimed, and every ratio below is given as the range over
the runs taken.

## The four gather shapes against Phase 267

The Phase 267 file's node section read its row-frame tree (its "before") and the dense frame after
it, on another machine: the inner join 57.0 against 76.5 ms (after / before 1.34), the 10,000-key
group-by 61.0 against 80.0 (1.31), the 50-on-value pivot 14.63 against 19.88 (1.36), the window
209.5 against 351.5 (1.68). As in the Phase 325 file, the row-frame figure on this machine is
estimated through 8a39a42, the successor of 267's dense tree: its harness figure divided by that
ratio. The harness, median ms:

| Shape | 8a39a42 | Row-frame estimate | Phase 326 | 326 / estimate |
|---|---:|---:|---:|---:|
| inner join 10,000 x 10,000 | 117.0, 122.0 | 87 to 91 | 25.0, 24.0 | **0.27 to 0.29** |
| group-by, 10,000 distinct keys | 130.0, 103.0 | 79 to 99 | 20.5, 23.3 | **0.21 to 0.29** |
| pivot, 50 on-values | 33.5, 32.0 | 23.5 to 24.6 | 33.0, 33.5 | **1.34 to 1.43** |
| window CumulSum, one partition | 435, 440 | 259 to 262 | 64.0, 100.0 | **0.24 to 0.39** |

**The pivot is not below its row-frame figure, and emission is not why.** Its profile on the phase's
tree puts 16% of the time in structural union equality, all but a sliver of it called from
`Column.aggregate` (the column layer, a package this repository consumes) once per (group,
on-value) pair, and 5% more in `aggregate` itself — 5,000 calls over one-cell lists for this
shape. The open slot table's probes are 1%. The row hasher had already taken the pivot's index
grouping (Phase 325); what is left is the aggregation per pair, which this phase does not reach.

## Phase 280's bar, on both hosts

An `int64` decimal vector would pay `BigInt` on node for every add and compare. Phase 280's `Decs`
vector already carries each decimal as an unscaled integer in a float64 at one scale per column,
admitted only up to `ScaledDecimal.maxExact` (2^53 - 1) — the candidate this phase asked for — so the
decimal kernels pay no `BigInt` on node: in the emitted JavaScript the only decimal-side `BigInt`
left is `ScaledDecimal.render`, once per output value. The node harness's typed family, the phase's
tree (median ms; 27710d5 in brackets):

| Verb | Rows | decimal | float | int |
|---|---:|---:|---:|---:|
| filter | 100,000 | 61.0 (198.0) | 103.0 (155.0) | 97.0 (142.0) |
| group-and-sum | 100,000 | 75.0 (127.0) | 38.0 (87.0) | 43.5 (76.0) |
| sort | 100,000 | 467 (596) | 340 (648) | 280 (554) |
| join | 10,000 | 93.0 (205.0) | 44.0 (98.0) | 26.5 (141.0) |

The integer `Sum` stream (Phase 323) still accumulates in `int64`, a `BigInt` per row on node. It
is not converted here: group-and-sum over ints reads 43.5 ms at 100,000 rows against 38.0 over
floats, which carry no `BigInt`, so the int64 accumulator costs at most that difference, and a
float-carried sum would need a deferral past 2^53 to stay exact.

## The tick family

The Release clock leg on the phase's tree, 15 of 15 green, nothing discarded as saturated. The 1,000-row
cases the CI margin is thin on: `filter > groupBy` 0.110 against 0.132 ms (x0.84), `filter > sort >
limit` 0.120 against 0.247 ms (x0.49); the inner join x1.00, the pivot x1.15, the window x1.30, all
under `tick <= 1.6 x full + floor`. The .NET tick path is unchanged by construction; these are the
leg's own figures, not a claim of improvement.

**Falsifier.** The parity claim is the two probe outputs comparing equal byte for byte; it was not
vacuous on the way here — before the sort's indexing went through `Raw.at`, the malformed-frame lines
for Sort differed between the hosts (node's helper appends `\nParameter name: index`), and before the
portable kernel checked its mask as a span, Filter over a short mask refused with a different message
on each host.
