# Compute benchmarks — 2026-09-27, Snapdragon X Elite (X1E80100)

The first recorded run of the Phase 262 harness, at the `0.33.0` draft of this repository's
sources. Every later performance change is measured against these tables on the same instrument.

## Machine and build

| | |
|---|---|
| Machine | Snapdragon X 12-core X1E80100, 3.40 GHz, 12 physical cores, Arm64 |
| OS | Windows 11 (10.0.26200) |
| .NET | SDK 10.0.400, runtime 10.0.11, Arm64 RyuJIT |
| Build configuration | Release (BenchmarkDotNet builds each measured process with `-c Release /p:Optimize=true`) |
| .NET instrument | BenchmarkDotNet 0.15.8, `MemoryDiagnoser`; one launch, three warm-ups, ten measured iterations per benchmark |
| node | v24.16.0, the harness compiled by Fable 5.0.0 |
| node instrument | the `Node/` harness: two warm-up calls, calls per sample doubled until a sample spans 50 ms, then seven samples |

**The figure is the median.** On .NET it is BenchmarkDotNet's `Median` column; `Allocated` is managed
bytes per operation, and "Allocated / row" divides it by the input row count. Node has no allocation
counter the harness can read, so its tables carry the median only.

How to reproduce: the README's "Benchmarks" section. The .NET tables were assembled from
BenchmarkDotNet's CSV reports (`--filter '*Sheet*'`, `'*Scaling*'`, `'*Shapes*'`); the node tables
are the harness's own output.

## The corpus, in one paragraph

**Sheet:** `orders(id:int, region:string over 5 values, qty:int, price:float in whole quarters)`, a
scalar `threshold` bound as a `Param`, node `lines` = `Derive amount = qty * price` then
`Derive big = amount >= threshold`, node `byRegion` = `Derive amount` then
`GroupBy region [Sum amount as total; Count as n]`. The **hand arm** is plain arrays and loops with a
full recompute of each node; its result is asserted equal to the evaluator's, cell for cell, before
anything is timed. **Scaling:** the suite's three `Scaling` pipelines over its four-column table, as
a full evaluation of a table with one row edited and as the restricted refresh over that one-row
delta (priming and diffing are setup). **Shapes:** an inner join of two 10,000-row tables on one int
key (every left row matches one right row), a group-by over 10,000 distinct string keys (20,000
rows), a pivot with 50 on-values over 100 index values (5,000 rows), a `CumulSum` window over one
partition of 100,000 rows, and a sort on two keys (a string over 100 values ascending, a permuted int
descending) over 100,000 rows.

## What the tables say

- **The hand arm is two to three orders of magnitude ahead.** At 100,000 rows the evaluator takes
  about 920 times the hand arm's time on `lines` and about 310 times on `byRegion`, and allocates
  about 1.4 KB per row where the hand arm allocates 9 bytes (its output arrays) or nothing.
- **Allocation per row is flat with size** on the row-local and grouping shapes (about 1.3 to 1.4 KB
  per row on the sheet, about 1.2 KB on the `Filter > GroupBy` pipelines): the cost is the per-cell
  representation, not an algorithmic blow-up.
- **Two shapes are super-linear, and it shows in the allocations**: the 10,000 x 10,000 inner join
  allocates about 21.6 GB per evaluation (about 2.3 MB per left row) and takes about 7 s; the pivot
  allocates about 2.8 GB over 5,000 rows.
- **The node leg cannot run every case.** Under node the reference evaluator exceeds the JavaScript
  call stack on a `Derive` over 10,000 rows or more, and on a group-by producing 10,000 groups. Each
  such row is reported as "not measured" with the host's message rather than dropped. The hand arm's
  node figures at those sizes are marked "unchecked on this host" because the agreement check needs
  the evaluator; the .NET leg checks the same generated inputs at every size.
