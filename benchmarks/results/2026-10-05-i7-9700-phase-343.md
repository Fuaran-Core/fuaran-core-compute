# Phase 343 — independent pipelines alongside one another over one prepared source, native x64

Intel Core i7-9700, 3.00 GHz, 8 physical cores (no SMT), Windows 11 (10.0.26200.9457), .NET SDK
10.0.401, runtime 10.0.12, X64 RyuJIT x86-64-v3; every run printed `instrument: X64 process on a X64
machine`. BenchmarkDotNet 0.15.8, `MemoryDiagnoser`, one launch, three warm-ups, ten measured
iterations. **The figure is the median, in microseconds.** The harness is
`benchmarks/Fuaran.Core.Compute.Benchmarks/Concurrent.fs`; every setup holds each arm's answers equal
to `DataFrame.evalToPrepared`'s, pipeline for pipeline, before anything is timed, and `--check` runs
the same agreement over every arm, count and size.

```powershell
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks -- --filter '*Concurrent.Batch*'
dotnet run -c Release --project benchmarks/Fuaran.Core.Compute.Benchmarks -- --filter '*Concurrent.Floor*'
```

**Sitting.** One evening sitting, 19:20 to 19:34. CPU load read 7% before the first run, and no other
`dotnet` or `fsc` process was running when it started; load was not sampled during the runs, so a
cell with a wide spread (named below) may carry interference.

**This is the x64 leg only.** The shard asks for both native machines; the Arm64 leg (Snapdragon
X1E80100) was not available to this session and is not here.

## The batch

N pipelines over the sheet's `orders` (`Corpus.ordersTable`), cycling four node shapes: `lines` (two
derives), `byRegion` (a derive and a grouping), the big lines (a derive and a filter on the
`threshold` param) and the top ten by amount (a derive and a fused sort-and-limit). Every result
stays prepared, as `evalManyToPrepared` answers it.

- **sequential** — in order on the caller's thread through the native member; each pipeline free to
  run its own morsels and partitions. What calling `evalToPrepared` per pipeline costs.
- **alongside** — on the pool, at most one per logical processor at once, each through
  `Kernels.oneThread`: the shipped bound, nothing nested fans out.
- **nested** — on the pool likewise, each through the native member, so a pipeline over enough rows
  fans out its own morsels inside the batch. Measured to price the bound; not kept.
- **host** — the shipped `DataFrame.evalManyToPrepared`, which chose sequential below
  `PipelineRows` and alongside above it. This run was taken with the provisional threshold of
  32,768 rows of work, so `host` reads as sequential at 4 x 1,000 and 16 x 1,000.

At one pipeline every arm is the sequential path (the `nested` arm's 1 x 1,000 pays `Parallel.For`
around one pipeline). Wide spreads: sequential 16 x 100,000 (standard deviation 7.1 ms on a 27.6 ms
median) and 64 x 100,000 (16.2 ms on 103.8 ms). Allocation is the same in every arm (34.7 MB at 16 x
100,000, 139 MB at 64 x 100,000); at 64 pipelines the gain falls to about 2 because the collector,
not the evaluator, is then the shared resource.

**Verdict.** Running independent pipelines alongside one another pays at every size measured from
four pipelines up: 1.5 to 3.0 times at 1,000 rows, 2.0 to 3.7 times from 10,000. **The nesting bound
costs nothing**: `nested` is within noise of `alongside` everywhere (4 x 100,000: 4,318 against
4,247; 16 x 10,000: 1,468 against 1,369), so letting a pipeline inside the batch fan out its own
morsels buys nothing once the batch already holds the cores.

## The floor

Two and four pipelines over small `orders`, the two arms the threshold chooses between.

| N | Rows | Work (N x rows) | sequential | alongside | sequential / alongside |
|---:|---:|---:|---:|---:|---:|
| 2 | 50 | 100 | 16.4 | 17.0 | 0.96 |
| 2 | 100 | 200 | 21.5 | 19.9 | 1.08 |
| 2 | 250 | 500 | 29.0 | 28.3 | 1.02 |
| 2 | 500 | 1,000 | 42.7 | 35.3 | **1.21** |
| 2 | 1,000 | 2,000 | 72.8 | 55.6 | **1.31** |
| 4 | 50 | 200 | 29.9 | 26.4 | 1.13 |
| 4 | 100 | 400 | 40.9 | 31.0 | 1.32 |
| 4 | 250 | 1,000 | 56.1 | 47.7 | **1.18** |
| 4 | 500 | 2,000 | 87.9 | 71.0 | **1.24** |
| 4 | 1,000 | 4,000 | 141.0 | 94.1 | **1.50** |

**The threshold that follows: `Kernels.PipelineRows` = 1,000 rows of work.** From 1,000 every batch
measured ran 1.18 times faster or more alongside; below it the readings run from 0.96 to 1.32 with a
few microseconds at stake either way, and the one loss (two pipelines over 50 rows) is below it.

**Not Phase 341's figure.** The shard asked for the threshold from Phase 341's native figures. Those
price splitting ONE step into morsels whose pieces are then gathered: the morsel `Filter` bought
nothing at 10,000 rows (two morsels) and paid at 100,000, which is where `PartitionRows` (32,768)
comes from. Taken as the batch threshold it would have run 4 x 1,000 and 16 x 1,000 sequentially, at
1.52 and 2.71 times the cost (the `host` column above, measured with 32,768 in place). A batch splits
nothing and gathers nothing, so its pieces pay from about thirty times less work.
