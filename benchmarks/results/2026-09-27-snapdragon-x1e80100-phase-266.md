# Compute benchmarks — 2026-09-27, Snapdragon X Elite (X1E80100), Phase 266

A follow-up to `2026-09-27-snapdragon-x1e80100.md` (the Phase 262 baseline at `f6b6054`). The
"before" column here is the tree at `2ce42cb` — Phases 263 to 265 landed (array rows and resolved
column indices, the hash join, the one-pass pivot, linear rolling windows, the allocation-free
grouping comparer) — and the "after" column is that tree plus Phase 266: each step's expression
compiled once into a closure tree specialised by a static typer, errors through one slot per row,
and the `Filter` / `Derive` row loops iterative. Same machine, same instrument, same corpus; only
the row-local shapes and the node leg are re-measured, because they are what the phase touches.

## Machine and build

| | |
|---|---|
| Machine | Snapdragon X 12-core X1E80100, 3.40 GHz, 12 physical cores, Arm64 |
| OS | Windows 11 (10.0.26200) |
| .NET | SDK 10.0.400, runtime 10.0.11, Arm64 RyuJIT |
| Build configuration | Release |
| .NET instrument | BenchmarkDotNet 0.15.8, `MemoryDiagnoser`; one launch, three warm-ups, ten measured iterations per benchmark |
| node | v24.16.0, the harness compiled by Fable through `run-node.ps1 -FableFrom` |
| node instrument | the `Node/` harness: two warm-up calls, calls per sample doubled until a sample spans 50 ms, then seven samples |

**The figure is the median**, as in the baseline file: BenchmarkDotNet's `Median` column on .NET,
the harness's median on node. `Allocated` is managed bytes per operation on .NET; node carries the
median only.

**The machine was not quiet.** A video call and several other sessions ran throughout (about 45%
CPU load and under 4 GB of free memory when checked), and a first pair of runs taken forty minutes
apart disagreed by 30 to 60% on paths this phase does not touch. So the .NET figures below come from
TWO INTERLEAVED PASSES — base, after, base, after, each pass a clean Release run of its own checkout
(`--filter '*Sheet*' '*Scaling*'`), one after another with nothing else of the operator's running —
and both passes are printed, `p1 / p2`, so the noise is visible beside the effect. The corpus check
(`--check`) was green on the after tree before anything was timed. A ratio is the after median over
the base median, averaged over the two passes.

The refresh rows go through the incremental seam, which this phase does not touch (it still
evaluates through the reference's `evalResolved`); they are the control, and they move within the
noise. The one-comparison `Filter` is a small share of the full runs, so the `filter-groupby` gains
are modest — but `filter-sort-limit: full` drops to 0.38 and sheds 36 MB, which is not the filter:
the reference's numeric comparison used to allocate two options per comparison and compare them
generically, and this phase routes it through one float comparison shared with the compiled
comparison kernel (so the two cannot disagree), which every sort comparison over numeric keys now
pays nothing for.

### The 129-node row expression at 20,000 rows

The scaling suite's costly shape — sixteen nesting levels of alternating integer addition and
subtraction, 129 expression nodes, as a `Filter` over a four-column table — timed through the same
Release build of the package from an F# script (three warm-ups, then the best of seven runs; three
such scripts per tree, interleaved). Not a BenchmarkDotNet case, so no allocation figure and wider
noise:

| Case | Rows | Before, best of 7 (ms, three scripts) | After, best of 7 (ms, three scripts) | After / before (best) |
|---|---:|---:|---:|---:|
| 129-node `Filter` | 20,000 | 39.30 / 34.66 / 39.15 | 49.84 / 18.92 / 20.88 | 0.55 |

The first after-script's 49.84 ms is the contended machine (its median was 61 ms against the other
two scripts' 36 and 24); the best-of-three-scripts is the figure the ratio uses. The typer compiles
every one of the sixty-four binary nodes to the integer kernel (the suite asserts it), so this is the
shape where the closure tree replaces the most `Result.bind` closures per row.

## node

The Phase 262 leg could not run the evaluator's `Derive` shapes at 10,000 rows or more, nor the
10,000-group group-by (`Maximum call stack size exceeded`); Phase 265 turned the group traversal
into a loop, and this phase does the same for the `Filter` and `Derive` row loops, so every cell

the "after" run under a lighter load: the shapes this phase does not touch (the join, the window,
the sort) measure 1.5 to 1.9 times slower in the after run than in the before run, and that
difference is the machine, not the tree. Read the node columns for what is now MEASURABLE, and read
the ratios with that in mind.

## Reading the numbers

- **On .NET the row-local shapes gain what an interpreter-to-closure compilation buys when the row
  loop is the whole run:** `lines` at 10,000 rows is 0.63 of its base and allocates 18% less; the
  129-node expression is 0.55. Where the row loop is a small share (the one-comparison scaling
  filters, the grouping shape), the gain is that share.
- **The comparison change is the larger effect on sorted pipelines** — a side effect of sharing one
  float comparison between the reference and the kernel, and it is certified by the same law
  corpus, byte-identical, as everything else here.
- **The 100,000-row figures are gen-2 bound**, and the next gain there is the representation
  (a dense column and a shared source between evaluations), not the expression.
- **Under node the previously unmeasurable cells now measure**, and the 10,000-row `Derive` shape
  is within the same order as the hand arm's overheads on that host; a like-for-like node
  before/after on a quiet machine is still owed, because the two node runs were not taken under one
  load and the before run's cells of interest could not run at all.
