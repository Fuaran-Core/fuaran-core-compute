# D735.1: a decision is a file of its own under `docs/decisions/`, named for the phase that made it and cited `D<phase>.<n>`; `DECISIONS.md` is closed at D91 and keeps every entry it holds

**Date:** 2026-11-28. **Phase:** 735.

**Context.** `DECISIONS.md` was 9,412 lines and held D1 to D91, newest first. Every change that recorded a
decision prepended its entry at the same line and took the next free number, so any two changes in flight that
each decided something conflicted on that file, and each could take the same number without knowing. D91 moved
the release record out of `STABILITY.md` for the same reason; this is the same move for the decision record. The
operator ruled on 2026-11-27 that a new decision is named for the phase that made it, `D<phase>.<n>`, so nothing
is allocated when it is written.

**Ruled.**

1. **A directory of decisions.** `docs/decisions/` holds every decision recorded from Phase 735 on, one file each,
   and nothing else.
2. **The file name is the decision's name.** `D<phase>.<n>.md`: `<phase>` the number of the phase in this
   repository's roadmap record that made the decision, zero-padded to four digits so a listing reads in phase
   order (the padding of D91's `phase-<n>.md`); `<n>` counts that phase's decisions from `1`, with no gap and no
   leading zero. The phase number exists before the decision is written, so two changes cannot pick one name. This
   file is `D0735.1.md`.
3. **The header.** A decision file's first line is `# D<phase>.<n>: <title>`, the phase without its padding, and
   its third is `**Date:** <yyyy-mm-dd>. **Phase:** <phase>.`, the date it was recorded. The body follows, in the
   shape `DECISIONS.md`'s entries have (context, what was ruled, what was considered).
4. **The citation.** A decision recorded here is cited `D<phase>.<n>` (`D735.1`), without padding, wherever a
   decision is cited: a source comment, a test, a law file's description, a release entry, another decision. The
   ninety-one decisions before it keep their names, `D1` to `D91`, cited as they always were, `DECISIONS.md`
   `D<n>`. The two forms cannot be confused: no `D<n>.<m>` citation existed before this one.
5. **`DECISIONS.md` is closed, not moved.** It holds D1 to D91, each once, and gains a head note saying so and
   pointing here. No entry in it is reworded, renumbered or moved, because the generated law files, `proofs.json`,
   `copies.json`, `version-derives.json`, the F\* sources, the proof ladder's rows and some forty source and test
   files cite those entries by that path, and every such citation still resolves. A later decision that revises
   one of them is a new file here that names it; the old entry is not edited.
6. **A change that decides something adds one file and edits `DECISIONS.md` not at all.**

**The guard.** Two properties join the `Package roster` family, beside the release record's, each with a go-red
case over synthetic input. **The closed record:** every `## ` heading in `DECISIONS.md` is an entry heading,
`## <yyyy-mm-dd> — D<n>: <title>`, and the numbers are exactly D1 to D91, each once, so a new entry above D91, an
entry in the new form written into the old file, a renumbering and a removal are each refused by name. **The
directory:** every name under `docs/decisions/` is `D<phase>.<n>.md` as item 2 has it, its header is item 3's
and names the same decision and phase as the file, and a phase's decisions run from `1` with no gap. Each was seen
to fail once on a wrong tree before it was trusted: a `## … — D92: …` entry added to `DECISIONS.md`, and a
decision file named against the form.

**Considered.** *A file per decision under the next free number* (`D92.md`) keeps the allocation, and with it the
collision this decision exists to remove. *Moving D1 to D91 into files* would break every citation by path for
nothing a reader needs. *An index file listing the decisions* would be one more file every decision edits, the
merge point this removes; the directory's listing is the index. *The guard in its own test file* was considered;
the roster family already holds the release record's layout to its rule, and the two records are one kind of
check.
